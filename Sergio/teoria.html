Teoria: da fila do banco ao popleft()

Esta página constrói o raciocínio em camadas: primeiro o problema (quem atender), depois a estrutura (três filas), depois o algoritmo (2:1), depois a lei e, por fim, o código e o banco. Cada seção existe porque a anterior não resolve tudo sozinha.

A frase que resume o projeto

Uma fila por nível legal, FIFO dentro de cada uma; 80+ sempre primeiro; quando não há 80+, duas chamadas da fila padrão para cada uma da convencional. O ciclo 2:1 é o que impede a fila comum de morrer de fome. O banco guarda o estado; o algoritmo decide a ordem; o Streamlit deveria ser a tela — mas essa última parte ficou na especificação.

1. Fila, FIFO e prioridade: o problema real

Uma fila é uma sequência de itens em que a saída acontece em uma extremidade e a entrada na outra. Quando a regra é First In, First Out (FIFO), o primeiro que chegou é o primeiro que sai. É o que o senso comum espera de uma fila de banco: quem chegou antes não pode ser ultrapassado indefinidamente.

Só que o banco não pode ser uma fila única. A lei manda dar atendimento prioritário a certos grupos. Se o banco simplesmente colocasse todo mundo na mesma fila, uma pessoa com 80 anos poderia esperar atrás de 200 clientes comuns. Se, no outro extremo, o banco criasse uma fila separada e só chamasse priority forever, a fila comum nunca andaria. O problema é combinar prioridade com progresso.

A palavra “prioridade” não significa “atendimento imediato” em toda e qualquer situação. Na lei, o termo aparece como atendimento prioritário: um tratamento diferenciado, que pode ser uma fila separada, um guichê exclusivo ou o atendimento imediatamente após o que estiver em curso. O projeto traduz isso em ordem de chamada.

2. Starvation e aging: o problema que o ciclo resolve

Starvation (inanição) é quando um processo ou cliente nunca recebe o recurso porque sempre existe alguém com prioridade maior. Em sistemas operacionais, o exemplo clássico é uma fila de baixa prioridade que nunca é escalada porque chegam processos de alta prioridade sem parar.

No banco, o cenário é: a fila padrão tem 300 pessoas; a convencional tem 1. Se o algoritmo sempre escolher a padrão enquanto ela não esvaziar, o cliente convencional espera até o fim do dia — ou para sempre, se a demanda não parar. O ciclo 2:1 força a chamada de um convencional a cada duas padrões, desde que ambos existam.

Existe outra solução clássica: aging (envelhecimento). A prioridade de um item aumenta conforme o tempo de espera. É o que um bom sistema operacional faz para não deixar nada morrer de fome. O projeto não usa aging por tempo; usa cota por contagem. Isso é suficiente para o exercício, mas não garante um limite máximo de espera em segundos. Se a banca perguntar “e se o convencional chegar às 9h e a fila padrão nunca parar?”, a resposta honesta é: “com 2:1 ele é chamado, no máximo, após duas padrões; o tempo real depende da duração de cada atendimento; para garantia por tempo eu precisaria de aging ou de um SLA”.

Starvation do 80+?

O ciclo 2:1 protege a convencional contra a padrão. Ele não protege ninguém contra a fila de 80+, que é absoluta. Se chegarem 80+ sem parar, as outras duas filas esperam. Isso é uma escolha de projeto — e um ponto que a banca pode explorar. Em um sistema real, seria preciso definir uma política para isso (por exemplo, limite de atendimentos consecutivos ou uma janela de prioridade).

3. Por que três filas e não uma heap?

Há duas formas clássicas de implementar prioridade:

  • Heap / fila de prioridade: uma única estrutura ordenada por uma chave. Inserção e remoção em O(log n). Se a chave for (nivel, data_chegada), o menor nível sai primeiro e, dentro dele, o mais antigo.
  • Filas multinível: uma fila FIFO por nível; a escolha de qual fila atender é feita por uma regra externa. Inserção e remoção são O(1); a “inteligência” fica no escalonador.

O projeto escolheu filas multinível porque o requisito não é só “respeitar a prioridade”, é garantir uma proporção entre padrão e convencional. Uma heap pura não sabe o que é “duas padrões para cada convencional”; ela só sabe qual é o próximo menor. Você poderia simular a cota com contadores e uma heap, mas o código ficaria mais confuso. Com três deques, a regra fica explícita: cada fila é uma linha; o contador diz de qual linha puxar.

4. collections.deque: a estrutura escolhida

Um deque (double-ended queue) é uma fila de duas pontas. Em CPython, ele é implementado como uma lista duplamente encadeada de blocos de ponteiros — não como uma lista contígua que precisa deslocar todos os elementos. Por isso append() e popleft() são O(1): o custo não cresce com o tamanho da fila.

OperaçãoComplexidadeUso no projeto
append(x)O(1)entrada de cliente no fim da fila
popleft()O(1)chamada do primeiro da fila
appendleft(x)O(1)rollback se a persistência falhar
len(d)O(1)tamanho das filas
acesso ao meio d[i]O(n)não é usado

Se você usasse uma list comum, pop(0) seria O(n), porque todos os elementos precisariam andar uma posição. Com 500 clientes isso é irrelevante; com 1 milhão, é a diferença entre um sistema que responde e um que trava. O PDF fala em “lista duplamente encadeada com blocos de memória”; a descrição correta é essa: deque é uma lista duplamente encadeada de blocos, não uma lista de elementos individuais com ponteiros para o anterior e o próximo.

Detalhe de entrevista

deque não é thread-safe para operações compostas. append e popleft isolados são atômicos sob o GIL, mas “verificar se está vazio e retirar” não é uma operação atômica. Com dois caixas chamando ao mesmo tempo, você precisa de Lock, transação ou uma fila no banco.

5. Weighted round-robin, quantum e a intuição do 2:1

Round-robin é revezamento: cada fila recebe uma vez, em turnos. Weighted round-robin é revezamento com peso: uma fila recebe mais turnos que a outra. No projeto, o peso é 2 para a padrão e 1 para a convencional. O “quantum” é a quantidade de chamadas antes de trocar de fila.

O ciclo funciona assim quando as duas filas têm gente:

  1. Etapa 0 (padrão): chama P1; contador = 1.
  2. Etapa 0 (padrão): chama P2; contador = 2; atinge o limite, avança para etapa 1 e zera.
  3. Etapa 1 (convencional): chama C1; contador = 1; atinge o limite, avança para etapa 0 e zera.
  4. Repete: P3, P4, C2, P5, P6, C3…
Ciclo 2:1 com as duas filas cheias
P1padrão · contador 1/2
P2padrão · 2/2 → troca
C1convencional · 1/1 → troca
P3padrão · 1/2
P4padrão · 2/2 → troca
C2convencional · 1/1

O nome “anti-starvation” é um pouco enganoso: a função não impede toda e qualquer inanição; ela garante que a convencional tenha uma cota. A fila de 80+ continua sendo estritamente prioritária. Em sistemas operacionais, o mesmo padrão aparece em escalonadores com múltiplas filas e feedback; a diferença é que lá o quantum costuma ser de tempo de CPU, não de número de chamadas.

6. Lei 10.048/2000: a base legal do atendimento em bancos

A Lei 10.048/2000 é a norma central do projeto. Ela não fala só de banco: fala de atendimento prioritário em repartições públicas, concessionárias de serviço público e instituições financeiras. O artigo 2º, parágrafo único, é a frase que você precisa saber de cor:

Texto-chave

“É assegurada, em todas as instituições financeiras, a prioridade de atendimento às pessoas mencionadas no art. 1º.”

O art. 1º, na redação atual (Lei 14.626/2023), lista: pessoas com deficiência, pessoas com transtorno do espectro autista, pessoas idosas com 60 anos ou mais, gestantes, lactantes, pessoas com criança de colo, obesos, pessoas com mobilidade reduzida e doadores de sangue. Os doadores têm uma regra especial: são atendidos depois de todos os demais prioritários e precisam de comprovante válido por 120 dias (art. 1º, §2º).

O art. 2º caput fala em “serviços individualizados que assegurem tratamento diferenciado e atendimento imediato”. O parágrafo único estende a prioridade a todas as instituições financeiras. O art. 6º, III, prevê que o descumprimento por instituição financeira sujeita o responsável às penalidades do art. 44 da Lei 4.595/1964.

O projeto usa a lei para justificar a fila de prioridade padrão. O que ele não faz: verificar documentação, distinguir subgrupos dentro da prioridade padrão, tratar doadores de sangue, garantir atendimento individualizado ou separar guichês. Ele só ordena a chamada.

7. Estatuto do Idoso e Lei 13.466/2017: o 80+

A Lei 10.741/2003 (Estatuto do Idoso, hoje Estatuto da Pessoa Idosa) define idoso como pessoa com 60 anos ou mais e estabelece, no art. 3º, §1º, I, o atendimento preferencial imediato e individualizado. A Lei 13.466/2017 acrescentou o §2º:

Texto-chave

“Dentre os idosos, é assegurada prioridade especial aos maiores de oitenta anos, atendendo-se suas necessidades sempre preferencialmente em relação aos demais idosos.”

Perceba a expressão “dentre os idosos”. A lei cria uma preferência dos 80+ sobre os idosos de 60 a 79, não uma categoria acima de gestantes, PCDs ou autistas. O projeto, porém, transforma os 80+ em SUPER_PRIORIDADE = 0 e os atende antes de todo mundo, sempre. Isso é uma decisão de modelagem: mais protetiva em relação ao idoso de 80+, mas não é a leitura literal do dispositivo. Se a banca cobrar, a resposta correta é separar as duas coisas.

Há ainda uma consequência prática: se você atende 80+ de forma absoluta, a fila de 80+ pode starvar as demais. Em um banco real, a política precisaria lidar com isso — por exemplo, limitar quantos 80+ consecutivos são chamados ou garantir que, após N chamadas, uma padrão seja atendida. O código não faz isso.

8. Lei 12.764/2012: TEA como pessoa com deficiência

A Lei 12.764/2012 institui a Política Nacional de Proteção dos Direitos da Pessoa com Transtorno do Espectro Autista. O ponto que interessa ao projeto está no art. 1º, §2º: a pessoa com TEA é considerada pessoa com deficiência para todos os efeitos legais. O art. 3º-A, incluído pela Lei 13.977/2020, cria a Ciptea e fala expressamente em prioridade no atendimento e no acesso a serviços públicos e privados, em especial nas áreas de saúde, educação e assistência social.

No código, a pessoa com TEA entra na prioridade padrão (nível 1), com o motivo "Pessoa com Transtorno do Espectro Autista - TEA (Lei 12.764/2012)". A inclusão é coerente com a lei, mas o projeto não pede a Ciptea nem verifica documentação. Ele confia no motivo informado. Em produção, isso seria um ponto de fraude e de proteção de dados.

9. Lei 13.146/2015 (LBI): PCD, obesidade e a alteração na 10.048

A Lei Brasileira de Inclusão define pessoa com deficiência como aquela que tem impedimento de longo prazo de natureza física, mental, intelectual ou sensorial, que, em interação com barreiras, pode obstruir a participação plena na sociedade. A lei também alterou a Lei 10.048/2000 para incluir os obesos no rol de atendimento prioritário (redação de 2015).

O projeto lista “Pessoa com obesidade (Lei 10.048/2000)” como motivo de prioridade padrão. A lei inclui os obesos no rol, mas não define um critério operacional de comprovação; o projeto também não. Na prática, o banco precisa decidir como reconhecer a condição (laudo, autodeclaração ou avaliação), e a LBI acrescenta a discussão sobre impedimento de longo prazo e barreiras. É uma simplificação acadêmica, não um protocolo jurídico.

A mesma LBI é a base para tratar acessibilidade física, atendimento preferencial e adaptações. O projeto só modela a ordem da fila; não trata rampa, assento, comunicação acessível ou tempo de atendimento.

10. Lei 14.626/2023: o que mudou e o que o projeto não cobre

A Lei 14.626/2023 deu nova redação ao art. 1º da Lei 10.048 e incluiu expressamente pessoas com transtorno do espectro autista, pessoas com mobilidade reduzida e doadores de sangue. Também permitiu atendimento prioritário por postos, caixas, guichês, linhas ou atendentes específicos e, quando não houver estrutura separada, determinou atendimento imediatamente após a conclusão do atendimento em andamento, antes de quaisquer outras pessoas.

11. A hierarquia do código × a hierarquia da lei

O código tem três níveis. A lei tem um conjunto de grupos prioritários e uma preferência especial dentro do grupo dos idosos. A tradução não é automática:

Como defender a escolha

“Modelamos 80+ como prioridade absoluta para garantir a preferência especial do Estatuto. Reconheço que a lei diz ‘dentre os idosos’; em produção, eu validaria a política com o jurídico e trabalharia com uma fila de prioridade especial, não necessariamente acima de todos os grupos.” Essa resposta mostra domínio, não insegurança.

12. Cliente: dataclass imutável

O modelo de domínio está em modelos.py:

@dataclass(frozen=True)
class Cliente:
    id: str
    nome: str
    nivel_prioridade: NivelPrioridade
    motivo: str
    data_chegada: datetime
    status: StatusCliente = StatusCliente.AGUARDANDO

@dataclass gera __init__, __repr__ e __eq__ a partir dos campos. frozen=True impede atribuição depois da criação: cliente.nome = "x" levanta FrozenInstanceError. Isso protege o contrato entre camadas: o objeto que sai do extrator não é alterado por acidente pelo gerenciador.

O método criar() é uma fábrica simples que gera uuid4() e datetime.now(). Duas consequências: (1) o timestamp é naive (sem timezone), enquanto o banco usa TIMESTAMPTZ; (2) o id é gerado localmente, mas o banco também tem um UUID default — os dois podem divergir. O modelo não tem campo cpf, embora o extrator e o gerador usem CPF. Isso será importante no bug do id (seção 24).

13. NivelPrioridade: IntEnum e números mágicos

O projeto usa IntEnum para dar nome aos níveis:

class NivelPrioridade(IntEnum):
    SUPER_PRIORIDADE = 0
    PRIORIDADE_PADRAO = 1
    CONVENCIONAL = 2

IntEnum é um enum cujos membros são inteiros. Isso permite comparar, somar e serializar como número — útil porque o Supabase armazena nivel_prioridade como INT. O lado ruim é que a ordem numérica é o inverso da prioridade: 0 é o mais prioritário, 2 é o menos. Se alguém ordenar uma lista “do maior para o menor” achando que o maior número é o mais importante, a fila inteira inverte.

O código evita números mágicos na maior parte do tempo, mas ainda os usa em comparações: nivel == 0, indice not in (0, 1, 2). O ideal seria comparar sempre com o enum e centralizar a conversão. Também falta um método explícito de rank (por exemplo, prioridade_rank) para deixar claro que menor = mais prioritário.

14. StatusCliente e a transição que ninguém faz

O Python define apenas dois status:

class StatusCliente(Enum):
    AGUARDANDO = "aguardando"
    ATENDIDO = "atendido"

O banco define quatro: aguardando, em_atendimento, atendido, cancelado. Já existe um desalinhamento de contrato. Pior: o GerenciadorFilas não altera o status de ninguém. O docstring diz explicitamente que transições são responsabilidade da camada de persistência (Frente 1), mas essa camada não existe no repositório.

Então, quando a API chama um cliente, o objeto devolvido continua com status=AGUARDANDO. O teste test_gerenciador_nao_altera_status confirma isso. O sistema não marca o cliente como atendido, não grava em atendimentos e não muda para em_atendimento. Em uma demo real, você chamaria o mesmo cliente de novo se recarregasse a fila do banco. É uma das maiores lacunas do projeto.

15. GerenciadorFilas: o que ele guarda

A classe tem três deques e dois contadores:

16. aplicar_starvation() linha a linha

Esta é a função mais importante do projeto, em Alexandre.py:

def aplicar_starvation(fila_super, fila_padrao, fila_convencional,
                       etapa, contador, limites=(2, 1)):
    if not (fila_super or fila_padrao or fila_convencional):
        return None, None, 0, 0

    if fila_super:
        cliente = fila_super.popleft()
        return cliente, fila_super, etapa, contador

    filas_ciclo = (fila_padrao, fila_convencional)
    for _ in range(2):
        fila = filas_ciclo[etapa]
        limite = limites[etapa]
        if contador >= limite or not fila:
            etapa = (etapa + 1) % 2
            contador = 0
            continue

        cliente = fila.popleft()
        contador += 1
        if contador >= limite or not fila:
            etapa = (etapa + 1) % 2
            contador = 0
        return cliente, fila, etapa, contador

    return None, None, etapa, contador

Vamos por partes:

  1. Fila totalmente vazia: devolve None e zera etapa/contador. O reset é razoável: sem ninguém, o ciclo não tem estado útil.
  2. 80+: se houver qualquer super, ele sai imediatamente. A função devolve a etapa e o contador sem alteração. É isso que garante que um 80+ no meio do ciclo não reinicie a contagem de padrão/convencional.
  3. Ciclo: olha a fila da etapa atual. Se o contador já atingiu o limite ou a fila está vazia, avança a etapa e zera, e tenta a outra. O for _ in range(2) limita a duas tentativas — suficiente porque só há duas etapas.
  4. Chamada: remove o primeiro, incrementa o contador. Se atingiu o limite ou a fila ficou vazia, avança e zera. Observe: se a fila esvaziou antes do limite, o ciclo não “desperdiça” chamadas; ele já passa para a outra.
  5. Fallback: se as duas etapas falharem, devolve None. Isso só acontece em estados estranhos (por exemplo, ambas as filas vazias, mas a checagem inicial já cobriu).
O nome engana

A função se chama aplicar_starvation, mas ela combate a starvation. O nome correto seria escalonar ou aplicar_anti_starvation. Em uma apresentação, diga “a função implementa a política anti-inanição” e não “aplica starvation”, para não entregar uma ambiguidade de graça.

18. Filas vazias: o ciclo não desperdiça chamadas

Suponha que só haja convencionais. A etapa começa em 0 (padrão), a fila padrão está vazia. O laço vê not fila, avança para 1, zera e tenta de novo. A etapa 1 tem gente, então chama o convencional. Depois da chamada, como o limite é 1, avança para 0 e zera. Na próxima, repete o salto. Resultado: todos os convencionais saem em ordem, sem chamadas vazias.

O teste test_ciclo_encurta_quando_prioritarias_vazias confirma: 1 super + 5 convencionais produz S1 e depois só convencionais. O teste test_fila_convencional_vazia_nao_quebra confirma o outro lado: 4 super + 4 padrão, oito chamadas, e a nona devolve None.

Há um detalhe sutil: quando a fila padrão tem apenas 1 pessoa, o contador chega a 1 e a fila fica vazia; o código avança a etapa e zera. Isso não é um bug; é a forma de evitar que o ciclo fique preso em uma etapa sem gente.

19. 80+ no meio do ciclo: o contador não reinicia

Este é o teste mais elegante do projeto. Sequência: P0 (padrão), chega S0 (80+), depois P1 e C0. O esperado é P0, S0, P1, C0. Se o 80+ resetasse o ciclo, o resultado seria P0, S0, P1, P2... e a convencional seria adiada. O código preserva etapa e contador ao atender super, então o ciclo retoma exatamente de onde parou.

Isso é justo? Depende do ponto de vista. Para o convencional, sim: a chegada de um 80+ não zera o crédito que ele já tinha. Para o 80+, irrelevante: ele é atendido na hora. Para o sistema, é uma decisão de consistência. A banca pode perguntar “por que não resetar?”. A resposta é: “porque resetar puniria a fila comum duas vezes — uma pela interrupção e outra pela perda do progresso”.

20. 3:2:1 × 2:1: a contradição central

O PDF, o README e o arquivo Documentação/tarefas falam em 3 super, 2 padrão e 1 normal. O código não faz isso. Ele usa _limites = (2, 1) e trata 80+ como prioridade absoluta, sem cota. A documentação está desatualizada em relação à implementação.

FonteO que dizO que o código faz

Documentação/tarefas“3 superprioridades, 2 prioridades padrão e 1 normal”80+ absoluto, depois 2:1

Qual é a consequência de um 3:2:1 real? Em um ciclo de 6 chamadas, você chamaria 3 super, 2 padrão e 1 convencional. Isso faria sentido se “super” fosse só mais uma fila com peso. Mas o projeto escolheu dar aos 80+ prioridade absoluta, o que é incompatível com uma cota de 3: se houver 4 super, o quarto não espera o próximo ciclo. Você não pode ter as duas coisas ao mesmo tempo. A implementação resolveu a favor da prioridade absoluta e reduziu o ciclo a 2:1.

Resposta pronta para a banca

“A documentação fala em 3:2:1, mas o código implementa 80+ absoluto e ciclo 2:1. A suíte de testes confirma 2:1. Eu considero a documentação desatualizada; se o requisito fosse 3:2:1 literal, eu teria que remover a prioridade absoluta e criar um contador para super, o que mudaria o comportamento.”

21. Complexidade e custo real

Com deque, cada chamada é O(1); carregar a fila é O(n log n) por causa do sort_values do pandas; a memória é O(n). O algoritmo em si não percorre a fila inteira: ele só olha a cabeça de duas filas.

O gargalo real não é o algoritmo: é a rede. Toda chamada que recarrega do Supabase faz uma requisição HTTP e converte JSON em DataFrame. Para 500 clientes, isso é rápido; para milhares, você paginaria e manteria a fila em memória, sincronizando apenas as mudanças.

22. Supabase e PostgreSQL: por que não um banco local?

Supabase é uma plataforma que oferece PostgreSQL gerenciado, API REST automática (PostgREST), autenticação, storage e outras ferramentas. O projeto usa dois recursos: o banco e a API REST. Não usa autenticação de usuário, Edge Functions nem Realtime.

A vantagem é não precisar escrever um backend: o SDK supabase-py fala com a API REST e o PostgREST traduz para SQL. A desvantagem é que o banco fica na nuvem: sem internet, o sistema não carrega. Para um trabalho acadêmico, isso é aceitável; para uma demo na banca, é um risco. Tenha um plano B (um DataFrame local ou um dump).

23. PostgREST, REST e RLS: o caminho de uma requisição

Quando o código faz GET {SUPABASE_URL}/rest/v1/clientes_fila?apikey=..., o PostgREST monta um SELECT em clientes_fila, aplica as políticas de Row Level Security e devolve JSON. O apikey identifica o projeto; a chave publishable é pública por design, mas só deve permitir o que as políticas permitirem.

Aqui está o problema: as políticas do projeto são USING (true) para todas as operações. Isso significa que qualquer portador da chave pública pode ler, inserir, atualizar e apagar clientes. RLS está “ligado”, mas sem restringir nada. Em produção, você precisaria de autenticação, políticas por papel (atendente, gerente, caixa), auth.uid() e separação entre leitura pública e escrita autenticada.

Nunca coloque a chave real no site

O README do repositório contém uma URL e uma chave que parecem reais. Este site não as reproduz. Se você for apresentar, use placeholders no slide e mantenha o .env fora do Git. O .gitignore do projeto já prevê isso, mas a chave que vazou no README continua no histórico.

24. ExtratorFila, pandas e o bug do id

O extrator monta a URL e lê o JSON:

self.df = pd.read_json(self.url)
self.df = self.df.drop(columns=["id", "id_motivo"], errors="ignore")
return self.df

Ele remove id e id_motivo. Depois, o gerenciador tenta montar o cliente com row.get("id") or row.get("cpf") or uuid4(). Como id foi removido, o identificador vira o CPF. Isso tem três efeitos: (1) o campo id do Cliente deixa de ser o UUID do banco; (2) o CPF passa a ser usado como chave, mas o modelo não tem campo cpf; (3) se o CPF for nulo, cai no UUID aleatório, que não existe no banco.

Por que o extrator remove o id? Provavelmente para evitar conflito com o índice do DataFrame ou porque a versão inicial não usava o UUID. É um resquício. A correção seria manter o id e remover apenas id_motivo, ou mapear explicitamente id para o modelo.

Outro ponto: pd.read_json(url) faz uma requisição sem timeout explícito, sem tratamento de erro e sem paginação. Se o Supabase devolver um erro JSON, o pandas pode interpretar como DataFrame vazio ou levantar exceção. Em produção, use requests com timeout e valide o status.

25. Faker, random e a distribuição 15/35/50

O gerador escolhe a categoria com random.choices([0, 1, 2], weights=[0.15, 0.35, 0.50], k=1). Em média, 15% dos clientes são 80+, 35% são prioridade padrão e 50% são convencionais. Isso cria uma fila realista: a convencional é maioria, a padrão é uma minoria relevante e a super é rara.

O Faker entra depois: gera nome, CPF e data de nascimento compatível com a categoria. Para 80+, usa minimum_age=80, maximum_age=105. Para os motivos padrão, cada um tem uma faixa de idade (gestante 18–45, idoso 60–79, etc.). Para convencional, 18–59. O CPF gerado é sintético e tem dígito verificador válido — mas não é um CPF real; não use para nada além de teste.

Limitações: random não é criptograficamente seguro, mas aqui não precisa ser. O gerador não insere data_chegada; o banco preenche com now(). Se você inserir 500 em lote, todos podem ter timestamps muito próximos; a ordem FIFO dentro do lote pode depender da ordem de inserção. Para um teste de fila, isso é aceitável, mas não é uma simulação de chegadas ao longo do dia.

26. .env, python-dotenv e configuração

O projeto carrega SUPABASE_URL e SUPABASE_KEY do ambiente com load_dotenv(). O .env.example mostra as chaves vazias; o README mostra um exemplo preenchido (que não deve ser usado). O .gitignore ignora .env.

Boas práticas: nunca commitar o .env; usar chaves diferentes para desenvolvimento e produção; rotacionar a chave que apareceu no README; e nunca expor a service_role no cliente. A chave publishable é pública, mas as políticas de RLS precisam ser restritivas.

27. Streamlit: o que é e o que o projeto faz com ele

Streamlit é um framework Python para construir interfaces de dados. Você escreve um script; cada interação faz o Streamlit reexecutar o script de cima a baixo. É ótimo para protótipos e dashboards, e é o que o PDF promete: um painel com a senha atual e um botão “Chamar Próximo”.

O que existe no repositório é streamlit.py, um script que conecta ao Supabase, mostra “Conectado com sucesso” e dois st.metric: quantidade de categorias e clientes na fila. Não há botão, não há chamada do gerenciador, não há session_state, não há TV de banco. A interface completa é especificação, não implementação.

Há ainda um problema de nome: o arquivo se chama streamlit.py, igual ao pacote streamlit. Quando o script roda com o diretório no sys.path, o import streamlit pode encontrar o próprio arquivo e falhar com AttributeError. O README manda rodar streamlit run app.py, mas não existe app.py. A correção óbvia seria renomear para app.py e rodar streamlit run app.py.

28. st.session_state: por que ele seria obrigatório

Como o Streamlit reexecuta o script a cada clique, variáveis locais são recriadas. Se você criasse GerenciadorFilas() no topo do script, cada clique perderia os contadores e o estado das filas. A solução é guardar o gerenciador em st.session_state, que persiste entre reruns da mesma sessão.

if "gerenciador" not in st.session_state:
    st.session_state.gerenciador = GerenciadorFilas(auto_carregar=True)

gerenciador = st.session_state.gerenciador

O PDF descreve isso corretamente na seção 12, mas o código não implementa. Se a banca pedir “mostre o botão”, você não tem o que mostrar. A resposta honesta é: “o núcleo está pronto; a camada de UI ficou como trabalho futuro”. Se quiser salvar a apresentação, implemente um protótipo mínimo antes: um botão que chama chamar_proximo() e exibe o nome, com o gerenciador no session_state.
