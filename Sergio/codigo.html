2. modelos.py: o contrato

from dataclasses import dataclass
from datetime import datetime
from enum import Enum, IntEnum
from uuid import uuid4


class NivelPrioridade(IntEnum):
    """Níveis de prioridade legal. IntEnum porque:
      1) O schema do Supabase armazena nivel_prioridade como Int;
      2) A hierarquia é ordinal (permite comparação direta).

    Base legal:
      - SUPER_PRIORIDADE:  Lei 13.466/2017 (80+ anos)
      - PRIORIDADE_PADRAO: Lei 10.048/2000 e Lei 12.764/2012
      - CONVENCIONAL:      sem previsão legal
    """
    SUPER_PRIORIDADE = 0
    PRIORIDADE_PADRAO = 1
    CONVENCIONAL = 2

O que esta parte faz no total: define os três níveis legais como números 0, 1 e 2 e associa cada um à lei correspondente.

Nota de leitura jurídica. O comentário do código cita a Lei 13.466/2017 como base do nível 80+. O código foi mantido fiel ao repositório original, mas o modelo de referência adotado neste guia é a Resolução TSE nº 23.759/2026, art. 14, §3º (antecessora: Res. TSE nº 23.736/2024, art. 100, §3º), que garante ao eleitor com mais de 80 anos preferência sobre os demais, independentemente do momento de chegada. Na banca, diga: “a base setorial é a Lei 10.048/2000 com o Estatuto da Pessoa Idosa; o 80+ absoluto segue o modelo da Justiça Eleitoral, que não rege bancos, mas inspira a decisão de projeto”. O trecho de chamada é o que mais rende pergunta:

def chamar_proximo(self):
    etapa_anterior = self._etapa
    contador_anterior = self._contador

    cliente, fila, nova_etapa, novo_contador = aplicar_starvation(
        self._fila_super,
        self._fila_padrao,
        self._fila_convencional,
        self._etapa,
        self._contador,
        self._limites,
    )
    self._etapa = nova_etapa
    self._contador = novo_contador

    if cliente is None:
        return None

    if self._repositorio is not None and hasattr(self._repositorio, "registrar_chamada"):
        try:
            self._repositorio.registrar_chamada(cliente.id)
        except Exception:
            self._etapa = etapa_anterior
            self._contador = contador_anterior
            fila.appendleft(cliente)
            raise

    return cliente
chamar_proximo() — leitura linha por linha
  • etapa_anterior = self._etapa — guarda a etapa antes da chamada, para rollback.
  • contador_anterior = self._contador — guarda o contador antes da chamada.
  • cliente, fila, nova_etapa, novo_contador = aplicar_starvation(...) — calcula quem será chamado.
  • self._etapa = nova_etapa — atualiza a etapa após a chamada.
  • self._contador = novo_contador — atualiza o contador.
  • if cliente is None: return None — se não houver fila, não há chamada.
  • if self._repositorio is not None and hasattr(...) — tenta registrar a chamada no repositório.
  • self._repositorio.registrar_chamada(cliente.id) — tenta gravar no banco.
  • except Exception: ... — se falhar, restaura etapa, contador e devolve o cliente à fila.
  • raise — repropaga o erro para cima.
  • return cliente — devolve o cliente chamado se tudo deu certo.

O que este bloco faz no total: chama o cliente correto, salva seus contadores e tenta persistir a chamada. Se a persistência falhar, desfaz o estado para não perder a senha.

O que está bom: o rollback restaura etapa/contador e devolve o cliente à cabeça da fila se a persistência falhar. Isso evita perder uma chamada. O que falta: não há transação com o banco, não há atualização de status, não há gravação em atendimentos, e o cliente retornado continua AGUARDANDO.

Outro detalhe: sincronizar_estado() com repositório não ordena por data_chegada; ele confia na ordem de listar_aguardando(). Se o repositório devolver fora de ordem, o FIFO quebra. E estado_contadores() usa o literal 2 para “padrão concluído”, em vez de self._limites[0]; se a cota mudar, o painel mente.

CREATE TABLE IF NOT EXISTS motivo_prioridade (
    id_motivo SERIAL PRIMARY KEY,
    id_prioridade INT NOT NULL REFERENCES tipo_prioridade(id_prioridade),
    descricao VARCHAR(255) NOT NULL UNIQUE
);

CREATE TABLE IF NOT EXISTS clientes_fila (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    nome VARCHAR(120) NOT NULL,
    cpf VARCHAR(14),
    data_nascimento DATE,
    nivel_prioridade INT NOT NULL REFERENCES tipo_prioridade(id_prioridade),
    motivo VARCHAR(255),
    id_motivo INT REFERENCES motivo_prioridade(id_motivo),
    status status_senha NOT NULL DEFAULT 'aguardando',
    data_chegada TIMESTAMPTZ NOT NULL DEFAULT now()
);

O que esta parte faz no total: cria as tabelas principais de prioridades, motivos e clientes, com validações e valores padrão.

Bloco 8.1 — tabelas principais (linha por linha)
  • CREATE TYPE status_senha ... — define os status possíveis.
  • CREATE TABLE tipo_prioridade — tabela de níveis de prioridade.
  • CREATE TABLE motivo_prioridade — tabela de motivos ligados ao nível.
  • CREATE TABLE clientes_fila — tabela principal de clientes na fila.
  • id UUID ... gen_random_uuid() — id automático.
  • nivel_prioridade ... REFERENCES — força nível válido.
  • status ... DEFAULT 'aguardando' — status inicial da senha.
  • data_chegada TIMESTAMPTZ ... now() — quando o cliente entrou.

CREATE INDEX IF NOT EXISTS idx_proximo_fila
    ON clientes_fila(nivel_prioridade, data_chegada)
    WHERE status = 'aguardando';

O que esta parte faz no total: cria um índice parcial para buscar rapidamente a próxima senha aguardando, ordenada por prioridade e chegada.

Bloco 8.2 — índice parcial (linha por linha)
  • CREATE INDEX idx_proximo_fila — cria índice.
  • ON clientes_fila(nivel_prioridade, data_chegada) — ordena por prioridade e chegada.
  • WHERE status = 'aguardando' — inclui só senhas não atendidas.

CREATE TABLE IF NOT EXISTS atendimentos (
    id_chamada UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    cliente_id UUID NOT NULL REFERENCES clientes_fila(id) ON DELETE CASCADE,
    guiche INT NOT NULL CHECK (guiche > 0),
    data_chamada TIMESTAMPTZ NOT NULL DEFAULT now(),
    data_finalizado TIMESTAMPTZ
);
Schema SQL — leitura linha por linha
  • CREATE TYPE status_senha AS ENUM (...) — cria lista de status possíveis no banco.
  • CREATE TABLE tipo_prioridade — tabela com IDs e descrições de prioridade.
  • CREATE TABLE motivo_prioridade — tabela de motivos, ligados à prioridade.
  • CREATE TABLE clientes_fila — tabela principal com cliente, status e data de chegada.
  • id UUID PRIMARY KEY DEFAULT gen_random_uuid() — identificador automático.
  • nivel_prioridade INT NOT NULL REFERENCES tipo_prioridade — força nível válido.
  • status status_senha NOT NULL DEFAULT 'aguardando' — status inicial da senha.
  • data_chegada TIMESTAMPTZ NOT NULL DEFAULT now() — hora de chegada com fuso.
  • CREATE INDEX idx_proximo_fila ... WHERE status = 'aguardando' — índice para buscar a próxima senha aguardando.
  • CREATE TABLE atendimentos — tabela de histórico de atendimentos.

O que este bloco faz no total: cria a estrutura do banco: prioridades, motivos, clientes, índice parcial e histórico de atendimento.

Bloco 8.3 — tabela de atendimentos (linha por linha)
  • CREATE TABLE atendimentos — cria histórico de chamadas.
  • id_chamada UUID ... gen_random_uuid() — id da chamada.
  • cliente_id UUID ... REFERENCES clientes_fila — liga a um cliente.
  • guiche INT ... CHECK (guiche > 0) — número do guichê válido.
  • data_chamada TIMESTAMPTZ ... now() — hora da chamada.
  • data_finalizado TIMESTAMPTZ — hora do fim, pode ser nulo.

O que esta parte faz no total: cria o histórico de atendimentos, ligado ao cliente e com guichê e datas.

O índice parcial é uma boa decisão: ele cobre a consulta “próximo aguardando, ordenado por nível e chegada”. Mas o app não usa essa consulta: ele carrega todos os clientes e ordena no pandas. O índice serve para uma consulta que o código ainda não faz.

As políticas são o ponto mais grave:

ALTER TABLE clientes_fila ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Permitir todas operacoes em clientes_fila"
    ON clientes_fila FOR ALL USING (true) WITH CHECK (true);
RLS aberta — leitura linha por linha
  • ALTER TABLE clientes_fila ENABLE ROW LEVEL SECURITY — ativa segurança por linha.
  • CREATE POLICY ... FOR ALL USING (true) WITH CHECK (true) — libera qualquer operação para qualquer um.

O que este bloco faz no total: cria uma política permissiva que permite leitura e escrita de qualquer pessoa com a chave pública.

Isso permite SELECT, INSERT, UPDATE e DELETE para qualquer portador da chave pública. Em um banco real, seria necessário separar leitura e escrita, usar autenticação e definir políticas por papel. O README contém uma chave que parece real; não a reproduza.
