Slide 2 · Introdução e Objetivo

Objetivo: justificar o projeto e apresentar a base legal. É o slide em que a banca decide se você domina o problema ou só o código.

Fala pronta (1:30) “O ponto de partida é uma agência com três grupos de direitos diferentes. A dificuldade não é só a fila física: é provar que a ordem de chamada respeita a lei. Se o sistema atende só prioridades, a fila convencional pode nunca ser chamada — é o starvation. Se atende só por chegada, descumpre a lei. Nosso objetivo foi automatizar essa decisão com Python, Streamlit e Supabase. A base legal tem duas camadas: a Lei 13.466/2017 criou a prioridade especial dos 80+ entre os idosos; as Leis 10.048/2000 e 12.764/2012 definem a prioridade padrão — idosos de 60 a 79, gestantes, PCD e TEA. E o ciclo 2:1 garante que o convencional não fique para sempre.”

Como explicar cada parte

BlocoO que explicarComo apresentar
Dificuldade na gestão de filas físicasO problema operacional: senha, guichê, tempo de espera e falta de transparência. A fila física não mostra se a lei está sendo cumprida.“Hoje a ordem depende de quem está no caixa; o sistema torna a regra explícita.”
Cumprimento rigoroso da legislaçãoPrioridade não é cortesia: é dever legal. A Lei 10.048/2000 cita instituições financeiras no art. 2º, parágrafo único.aponte para o bullet e diga “o banco está explicitamente no texto da lei”
Risco de starvationDefina em uma frase: “é quando uma categoria nunca é chamada porque sempre existe alguém de prioridade maior na frente”.use as mãos: uma fila alta que nunca esvazia e uma baixa parada
Solução integradaPython decide, Streamlit mostra, Supabase guarda. Três camadas, uma regra só.conte nos dedos: regra, tela, banco
Lei 13.466/2017Criou a prioridade especial dos maiores de 80 dentre os idosos. O projeto adota, para o nível 0, o modelo do TSE: preferência sobre todos, independentemente da chegada.“no banco, a base é 10.048 + Estatuto; o modelo de precedência absoluta vem da norma do TSE”

Ciclo anti-inaniçãoO convencional tem uma chamada garantida a cada três, quando a fila 80+ está vazia.“duas padrão, uma convencional” com dois dedos e um dedo
Cuidado jurídico que a banca vai testar

Não diga “a Lei 13.466 garante que o 80+ passa na frente de todos”. O texto legal fala em prioridade especial dentre os idosos. A precedência sobre todos os demais grupos é o modelo da Resolução TSE 23.759/2026, art. 14, §3º (antes, 23.736/2024, art. 100, §3º), adotado no projeto. A frase segura é: “a 13.466 cria a prioridade especial entre os idosos; o nível 0 do sistema segue o modelo do TSE, que dá preferência sobre todos, e essa escolha está documentada”.

Pergunta provável: “Então o sistema cumpre a lei?”

“As regras de prioridade estão implementadas e testadas: o nível 0 nunca é furado, e o ciclo 2:1 impede a inanição do convencional enquanto a fila 80+ esvazia. O que o software não resolve sozinho é o cadastro correto do cliente e a fiscalização da operação — para isso existem o motivo, o status e o registro de atendimento.”

Slide 3 · Banco de Dados

Objetivo: mostrar que a persistência não é um detalhe — ela garante integridade e segurança.

Fala pronta (1:20) “A persistência é o Supabase, que é PostgreSQL gerenciado com uma API REST pronta. O modelo tem quatro tabelas: clientes_fila, atendimentos e as tabelas de domínio tipo_prioridade e motivo_prioridade. A segurança não depende do cliente: o RLS está fechado — sem policy, a chave pública não lê nem escreve; o app usa a chave secreta service_role no servidor. E as operações críticas são funções SQL atômicas: chamar_cliente e finalizar_atendimento. Se dois guichês tentarem chamar o mesmo cliente, uma falha; se o guichê já tem atendimento aberto, a função recusa.”

Como explicar cada parte

CartãoO que explicarComo apresentar
Supabase / PostgreSQLPostgreSQL gerenciado, alta disponibilidade e API REST gerada pelo PostgREST. Vantagem: não manter servidor de banco; trade-off: dependência de fornecedor.“não é um banco local: é um Postgres na nuvem com API pronta”
Tabelas principaisclientes_fila guarda quem espera (id UUID, nome, CPF, nível, motivo, status, chegada). atendimentos guarda cada chamada (cliente, guichê, chamada, finalização). As duas de domínio normalizam tipo e motivo.desenhe no ar: duas tabelas grandes e duas pequenas de apoio
Segurança RLSRow Level Security: sem policy, a chave anônima é negada. As views usam security_invoker e o EXECUTE das funções foi revogado de anon. Só a service_role, que fica no servidor, opera.“a chave que o navegador vê não abre a porta”
Transações RPCAs funções PL/pgSQL rodam em uma transação: marcar em_atendimento + inserir o atendimento acontece junto ou não acontece. A função também barra guichê ocupado e cliente que já saiu de aguardando.“ou tudo, ou nada” — abra e feche as mãos
Pergunta provável: “Por que RPC e não INSERT direto?”

“Porque a regra é transacional e precisa ser atômica. Se o app fizesse dois INSERTs separados, uma falha no meio deixaria o cliente marcado como em atendimento sem registro, ou o contrário. A função SQL junta a checagem do guichê, a mudança de status e a criação do atendimento em uma transação. Além disso, ela concentra a regra no banco, então qualquer cliente — Streamlit ou outro — obedece à mesma restrição.”

Se a banca pedir para ver

Mostre supabase/migrations/20261107150000_seguranca_e_atendimentos.sql: os DROP POLICY, o REVOKE, as duas funções e o GRANT ... TO service_role. É a prova mais rápida de que a segurança não é slide.

Slide 4 · Extração de Dados

Objetivo: mostrar o caminho do dado, do banco até a memória, e por que a ordem de chegada é confiável.

Fala pronta (1:20) “A cada atualização, o sistema não confia só na memória: ele relê o estado do banco. O extracao.py monta a URL REST já filtrando status=aguardando e ordenando por data_chegada. A chave vai no header, não na URL. O pandas converte o JSON em DataFrame e o gerenciador distribui cada linha para o deque do nível certo. Pergunta provável: “Por que reler o banco a cada 5 segundos?”

“Porque o estado é compartilhado entre guichês e páginas. Se a fila vivesse só na memória de uma sessão, o guichê 2 não veria a chamada do guichê 1. A releitura com preservar_ciclo=True mantém a posição do 2:1, então o ciclo não recomeça a cada atualização. O custo é uma requisição a cada 5 segundos; o ganho é consistência.”

Slide 5 · Starvation: Algoritmo Anti-Inanição

Objetivo: este é o slide mais importante. Se a banca só entender uma coisa, que seja esta: 80+ é absoluto; o ciclo 2:1 é o que impede o convencional de morrer.

Fala pronta (2:00) “Este é o coração do projeto. Existem duas regras. A primeira: se há alguém com 80 anos ou mais, ele é chamado agora, em FIFO, e isso não altera o contador do ciclo. A segunda: quando a fila 80+ está vazia, o sistema atende duas vezes a prioridade padrão e uma vez a convencional. O contador não reinicia quando um 80+ chega no meio: ele pausa. Se a fila da vez está vazia, a etapa avança sem gastar chamada. Com isso, o convencional tem uma garantia de progresso a cada três chamadas — desde que a fila 80+ não esteja permanentemente cheia; nesse caso, a prioridade absoluta continua valendo, e isso é uma escolha legal, não um bug.”

Como explicar cada parte

BlocoO que explicarComo apresentar
Prioridade absoluta (80+)Se a fila super tem alguém, é popleft e pronto. A função devolve a etapa e o contador inalterados.bata a mão na mesa: “esta passa na frente, ponto”
FIFO estritaDentro dos 80+, vale a ordem de chegada. Não é “o mais idoso primeiro”: é quem chegou primeiro entre os 80+.“a lei cria o grupo; a fila resolve o empate”
Preserva contadoresO 80+ é uma interrupção, não parte do ciclo. Ele não zera o 2:1; o ciclo retoma de onde parou.faça uma pausa e diga “pausa, não reset”
Ciclo ponderado 2:1Quando não há 80+, a sequência é Padrão → Padrão → Convencional. É um weighted round-robin com cotas (2, 1).dois dedos, um dedo, repita no ar
Sequência padrãoNão é 3:2:1. O README e o PDF antigos falam 3:2:1, mas o código e os testes fazem 2:1. Assuma a divergência antes que a banca aponte.“a documentação estava desatualizada; a verdade está no teste”
Avanço automáticoSe a fila da etapa está vazia, o algoritmo troca de etapa sem devolver None e sem desperdiçar chamada.“fila vazia não trava a esteira”

A pergunta que derruba: “e se a fila 80+ nunca esvaziar?”

Não invente que o ciclo resolve isso. A resposta honesta: “se a fila 80+ for infinita, o convencional espera por decisão legal — a prioridade absoluta prevalece. O ciclo 2:1 garante progresso quando a fila 80+ esvazia, que é o cenário operacional normal. Para o cenário extremo, a solução é operacional: mais guichês ou uma fila separada, não mudar a regra.”

Pergunta provável: “Por que não usar uma heap de prioridade?”

“Porque a regra não é só ‘maior prioridade primeiro’: existe um ciclo entre duas filas e uma exceção absoluta. Com três deques, append e popleft são O(1) e a regra fica explícita em uma função de vinte linhas. Uma heap daria O(log n) e esconderia a política de justiça dentro do comparador. Para três níveis e uma cota fixa, o deque é mais simples de explicar e de testar.”

Slide 6 · Gerenciador de Fila

Objetivo: mostrar quem executa a regra e como o sistema se protege de concorrência e falha.

Fala pronta (1:20) “O GerenciadorFilas é o orquestrador. Ele mantém três deques independentes. O escalonamento é delegado para aplicar_starvation, que recebe as três filas e devolve o cliente e a fila de origem. O acesso é protegido por um threading.Lock compartilhado por todos os guichês — um gerenciador por servidor, para o ciclo valer para a agência inteira. E há rollback: se o banco recusar a chamada, o cliente volta para a frente da fila e os contadores voltam ao valor anterior.”

Como explicar cada parte

CartãoO que explicarComo apresentar
Estrutura em três filasTrês deque: super, padrão e convencional. Separação física evita comparar níveis a cada chamada e deixa a política legível.desenhe três caixas lado a lado
Regras de escalonamentochamar_proximo() chama a função pura e atualiza etapa/contador com o que ela devolve. A regra não fica espalhada pelo gerenciador.“o gerenciador não decide a ordem; ele executa a decisão”
Controle de concorrênciaconexao.get_gerenciador() é cache_resource: um gerenciador por servidor, com um threading.Lock. As páginas usam with lock: em volta de sincronizar + chamar.“um guichê por vez entra na seção crítica”
Resiliência e rollbackAntes da chamada, o gerenciador guarda etapa e contador. Se o repositório lançar erro, restaura os dois e faz appendleft do cliente.“o cliente não desaparece nem pula a vez por causa de uma falha de rede”
Pergunta provável: “O lock resolve concorrência em produção?”

“Resolve dentro de um processo. Se houver duas instâncias do Streamlit, cada uma tem seu lock; por isso a garantia final é o RPC no banco, que checa se o cliente ainda está aguardando e se o guichê está livre. Para várias instâncias, o próximo passo seria uma transação com SELECT ... FOR UPDATE ou uma fila no próprio banco. O lock é a primeira camada, não a única.”

Frase de efeito

“O algoritmo é puro; o gerenciador é quem dá estado, ordem e segurança para ele.”

Pergunta provável: “Por que iframe e não componentes do Streamlit?”

“Porque o painel é uma TV: precisa de layout fixo, tipografia condensada e atualização suave. Com componentes nativos, cada rerun do Streamlit redesenha a página e pisca. Não venda “segurança” além do que existe

A senha é única e compartilhada, comparada no servidor. Isso é adequado para a demonstração, mas não é login individual com auditoria. Se perguntarem, diga: “é uma senha operacional única; para produção, o próximo passo é autenticação por operador com registro de quem chamou o quê”.

Slide 8 · Testes, Resultados e Conclusão

Objetivo: provar que a regra funciona e fechar com honestidade sobre o que falta.

Fala pronta (1:30) “Para validar, geramos dados sintéticos com Faker na proporção do projeto: 15% 80+, 35% padrão, 50% convencional. Os 18 testes cobrem prioridade absoluta, FIFO, ciclo 2:1, filas vazias, preservação do contador, rollback e o caminho de integração — o teste real do Supabase é pulado quando não há credenciais. O teste de falha simula o banco recusando a chamada: o cliente volta para a fila e o contador volta ao valor anterior. O resultado é uma solução integrada: regra, banco e interface. As pendências para produção são de hardening: login por operador, observabilidade, teste de carga e política de retenção/LGPD.”
