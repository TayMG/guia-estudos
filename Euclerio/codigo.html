1. api/main.py — a API

from fastapi import FastAPI, HTTPException
import psutil
import subprocess

app = FastAPI(title="Process Manager API")

# ---------- LISTAR ----------
@app.get("/processes")
def list_processes():
    """Lista todos os processos em execução"""
    processes = []
    for proc in psutil.process_iter(['pid', 'name', 'username', 'status']):
        try:
            processes.append(proc.info)
        except (psutil.NoSuchProcess, psutil.AccessDenied):
            pass
    return {"total": len(processes), "processes": processes}

# ---------- INSPECIONAR ----------
@app.get("/processes/{pid}")
def inspect_process(pid: int):
    """Inspeciona um processo específico pelo PID"""
    try:
        proc = psutil.Process(pid)
        return {
            "pid": proc.pid,
            "name": proc.name(),
            "status": proc.status(),
            "cpu_percent": proc.cpu_percent(),
            "memory_percent": proc.memory_percent(),
            "cmdline": proc.cmdline(),
            "username": proc.username()
        }
    except psutil.NoSuchProcess:
        raise HTTPException(status_code=404, detail=f"Processo {pid} não encontrado")
    except psutil.AccessDenied:
        raise HTTPException(status_code=403, detail="Acesso negado ao processo")

# ---------- INICIAR ----------
@app.post("/processes/start")
def start_process(command: str):
    """Inicia um novo processo"""
    try:
        proc = subprocess.Popen(command.split())
        return {"pid": proc.pid, "status": "iniciado", "command": command}
    except Exception as e:
        raise HTTPException(status_code=500, detail=str(e))

# ---------- ENCERRAR ----------
@app.delete("/processes/{pid}")
def terminate_process(pid: int, force: bool = False):
    """Encerra um processo pelo PID"""
    try:
        proc = psutil.Process(pid)
        if force:
            proc.kill()
        else:
            proc.terminate()
        return {"pid": pid, "status": "encerrado", "force": force}
    except psutil.NoSuchProcess:
        raise HTTPException(status_code=404, detail=f"Processo {pid} não encontrado")
    except psutil.AccessDenied:
        raise HTTPException(status_code=403, detail="Acesso negado")

Decisões dentro do código

Linha / escolhaPor que está assim
process_iter(['pid','name',...])passar os campos evita coletar tudo de todos os processos — é otimização, não estilo
try/except dentro do forprotege contra processo que morre durante a coleta — na prática o process_iter já ignora esses casos, então é defesa em profundidade
pid: into FastAPI valida e converte; /processes/abc devolve 422 automaticamente
HTTPException 404/403traduz a exceção do psutil para semântica HTTP correta
subprocess.Popen(command.split())não bloqueia a requisição e devolve PID; sem shell=True, logo sem injeção de shell
force: bool = Falsequery param opcional → ?force=true escolhe SIGKILL
Sem start_new_sessionnão é necessário em container (sem terminal); é a evolução natural, não um defeito
Três detalhes que podem virar pergunta

1. command.split() não entende aspas: sh -c "sleep 60" vira quatro argumentos com as aspas literais. O correto seria shlex.split(command).

2. cpu_percent() sem intervalo devolve 0.0 na primeira chamada, porque precisa de duas amostras de tempo de CPU.

3. O try/except da listagem está em volta do append, que não levanta exceção. O process_iter com attrs já descarta internamente processos que morrem no meio. Funciona, mas é redundante — e é uma ótima resposta para "o que você melhoraria?": mover a proteção para o ponto certo ou removê-la.

Nenhum dos três afeta o que o edital pede. Saber apontá-los mostra leitura crítica do próprio código.

1.1 api/requirements.txt — por que as versões são fixas

fastapi==0.104.1
uvicorn==0.24.0
psutil==5.9.6

O == não é detalhe de estilo: é reprodutibilidade. Sem ele, um pip install feito meses depois poderia trazer uma versão nova com mudança de comportamento, e o build passaria a gerar uma imagem diferente a partir do mesmo código. A banca pode perguntar "por que não usar a última versão?" — a resposta é que o projeto precisa ser reproduzível na máquina de qualquer integrante e no dia da apresentação, não que a versão seja a mais nova.

PacoteVersãoPara que serveO que aconteceria sem ele
fastapi0.104.1rotas, validação por type hints e OpenAPI/Swaggera API não sobe
uvicorn0.24.0servidor ASGI que escuta a porta 8000não há quem receba a conexão HTTP
psutil5.9.6leitura de /proc e envio de sinaisas rotas de processos não funcionam

O --no-cache-dir no Dockerfile é complementar: ele evita guardar o cache do pip dentro da imagem final. E a ordem COPY requirements.txt → RUN pip install → COPY main.py faz o cache de camadas funcionar: mudar o código não reinstala as dependências.

1.2 O ciclo de vida de um processo criado pela API

Quando alguém chama POST /processes/start?command=sleep%2060, o FastAPI executa subprocess.Popen(["sleep", "60"]). O que acontece no kernel, em ordem:

  1. O Python faz fork(): nasce um processo filho com o mesmo espaço de endereçamento, mas cópia separada.
  2. O filho faz execve() e passa a executar /usr/bin/sleep — agora é outro programa, com o mesmo PID.
  3. O pai (uvicorn) não espera: Popen retorna imediatamente com proc.pid. É por isso que a rota responde em milissegundos, mesmo que o comando dure uma hora.
  4. Quando o filho termina, ele vira zumbi até alguém ler o código de saída com wait()/waitpid().

Aqui entra a nuance que quase ninguém sabe: o módulo subprocess do Python faz uma colheita preguiçosa. A cada novo Popen, ele chama _cleanup() e faz poll() nos processos ativos; no __del__ do objeto ele também verifica. Então os zumbis deste projeto não se acumulam sem limite — mas também não são colhidos no instante em que morrem. Se o processo demora a terminar e nenhum outro Popen acontece, ele pode ficar zumbi por um tempo. A resposta madura é: "funciona para o escopo, mas o correto seria um wait() explícito em uma thread ou um reaper, porque a API não pode depender de um efeito colateral do módulo."

Detalhe do PopenConsequência realComo explicar
Sem stdout=PIPEa saída do filho vai para o stdout do uvicorn e aparece em kubectl logs"herda os descritores do pai; não capturei porque a API só devolve o PID"
Sem wait()a rota não confirma que o comando terminou; só que foi criado"o contrato é iniciar e devolver o PID, não executar sincronamente"
Sem start_new_session=Trueo filho fica no mesmo grupo de processos do uvicorn"em container não há terminal; se o grupo receber SIGTERM, o filho também recebe"
command.split()não respeita aspas nem espaços escapados"o correto seria shlex.split(); sem shell=True não há injeção por ; ou |, mas ainda dá para chamar sh -c — por isso a allowlist é necessária"
Parâmetro command: strvira query param, não JSON body"POST /processes/start?command=...; para body seria preciso um modelo Pydantic"
Comando inexistenteFileNotFoundError → HTTPException 500"o 500 é genérico; o ideal seria 400/422 com a causa"

1.3 A parte que a banca vai apertar: segurança da API

A API foi feita para demonstrar controle de processos, não para produção. O código não tem autenticação, não valida o comando e aceita qualquer PID no DELETE. Com hostPID: true, isso significa que qualquer pessoa que alcance o NodePort 30080 pode listar os processos do nó e tentar encerrar qualquer um — inclusive o kubelet, o etcd ou o próprio uvicorn.

RiscoPor que existe no códigoMitigação
Sem autenticaçãonenhum dependency de token/mTLStoken Bearer, mTLS ou OAuth2; ClusterIP + port-forward
DELETE em qualquer PIDpsutil.Process(pid) não tem allowlistrecusar PID 1, PIDs do control plane e do próprio processo; lista de alvos permitidos
POST com comando arbitrárioPopen(command.split()) executa o que vier — inclusive sh -callowlist de binários e argumentos; sem shell=True (já está correto, mas não basta sozinho)
NodePort expostotype: NodePort abre a porta no nóClusterIP + kubectl port-forward ou Ingress com auth
Root + CAP_KILLimagem não define securityContextrunAsNonRoot + capability mínima, ou isolamento em namespace privilegiado documentado
Sem auditoriaa API não registra quem chamoulog estruturado com identidade, IP e comando; audit policy no cluster
A resposta que ganha ponto

"O escopo pedia listar, inspecionar, iniciar e encerrar processos, e foi isso que implementamos. Para produção, a API não poderia ficar com NodePort e sem autenticação: eu trocaria por ClusterIP + port-forward, exigiria token, colocaria uma allowlist de PIDs e comandos, rodaria com o mínimo de capabilities e registraria auditoria. O hostPID continuaria sendo o risco central — ele é necessário para ver o /proc do nó, mas exige isolamento e controle de quem pode aplicar o Deployment."

3. api/Dockerfile

FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY main.py .
EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
  • python:3.11-slim — imagem oficial enxuta (~120 MB contra ~1 GB da completa). Não tem compilador, mas não precisamos.
  • Ordem requirements antes de main.py — o cache de camadas só invalida o pip install se as dependências mudarem.
  • --no-cache-dir — não guarda o cache do pip na imagem; economiza espaço.
  • --host 0.0.0.0 — sem isso o uvicorn escuta só em 127.0.0.1 dentro do container, e o Service nunca alcança. É o erro clássico de "funciona local, não funciona no Pod".
  • CMD em forma de lista (exec form) — o processo vira PID 1 direto, sem shell no meio, e recebe sinais corretamente.

4. nginx/Dockerfile — dois daemons em um container

FROM nginx:alpine

RUN echo '#!/bin/sh' > /entrypoint.sh && \
    echo 'busybox crond -b -l 8 -c /etc/crontabs' >> /entrypoint.sh && \
    echo 'nginx -g "daemon off;"' >> /entrypoint.sh && \
    chmod +x /entrypoint.sh

RUN echo "* * * * * date >> /usr/share/nginx/html/cron.txt" > /etc/crontabs/root

COPY html /usr/share/nginx/html

CMD ["/entrypoint.sh"]
ParteO que faz
nginx:alpinebase com nginx e busybox (que inclui o crond)
echo '...' > /entrypoint.shgera um script de inicialização de 2 linhas durante o build
crond -b -l 8-b = background (roda junto com o nginx), -l 8 = nível de log
nginx -g "daemon off;"mantém o nginx em foreground para o container não morrer
/etc/crontabs/rooto crontab do busybox; * * * * * = a cada minuto
date >> .../cron.txtacrescenta a data ao arquivo que o site mostra no iframe
Por que dois daemons no mesmo container?

Porque a página do Nginx precisa mostrar o log gerado pelo cron no mesmo filesystem. Como o arquivo está no mesmo sistema de arquivos, os dois processos ficam juntos. O terceiro container (cron-daemon) existe justamente para provar o agendador isolado. Se perguntarem "não é antipadrão?", a resposta honesta é: é, para produção — o correto seria um sidecar ou um volume compartilhado; aqui foi uma escolha de demonstração.

5. cron/Dockerfile

FROM alpine:latest

RUN echo "* * * * * date >> /var/log/cron-task.log" > /etc/crontabs/root

CMD ["busybox", "crond", "-f", "-l", "8", "-c", "/etc/crontabs"]

Diferença essencial em relação ao anterior: crond -f (foreground). Aqui o cron é o único processo, então ele precisa ficar em primeiro plano — se fosse -b, o container terminaria imediatamente.

6. nginx/html/index.html

Trecho essencial (o arquivo real também tem <style> com o CSS embutido da página):

<h1>Projeto A3 - Tema 1</h1>
<h2>Nginx + Cron Daemon</h2>
<p>Status: <strong>Servidor Nginx rodando!</strong></p>
<p>Log do Cron em tempo real (atualiza a cada minuto):</p>

<iframe src="cron.txt" title="Log do Cron"></iframe>

O iframe aponta para cron.txt, que está no mesmo diretório servido pelo Nginx. A cada minuto o crond acrescenta uma linha ao arquivo. É a prova visual de que dois daemons estão funcionando dentro do mesmo container.

“Atualiza em tempo real” é meia verdade

O arquivo é atualizado a cada minuto, mas o iframe carrega o cron.txt uma vez e não fica consultando o servidor. Para ver a linha nova, é preciso recarregar a página (ou adicionar <meta http-equiv="refresh" content="60">, ou um fetch periódico com JavaScript). O print mostra várias linhas porque a página foi recarregada depois de alguns minutos — não porque o iframe se atualiza sozinho. Se a banca perguntar “isso é tempo real mesmo?”, a resposta honesta é essa, e a melhoria é trivial.

CampoValorPor que
replicas2permitir self-healing sem tirar o serviço do ar

100m significa 0,1 CPU (100 milicores) — 10% de um núcleo. Como só há limite de CPU, o Pod da API é classe QoS Burstable. Os Deployments do Nginx e do cron não declaram resources, então seus Pods são BestEffort — detalhe que a banca pode cobrar e que quase todo grupo esquece.

O que dispara um novo ReplicaSet (e o que não dispara)

Alterar replicas não cria ReplicaSet novo: o mesmo RS é escalado. O que cria um RS novo é mudar o Pod template — imagem, variável de ambiente, recurso, label do template. Aí o Deployment faz rolling update e mantém o RS antigo para rollback. E há uma armadilha específica deste projeto: como a tag é sempre :latest e a política é Never, rebuildar a imagem não muda o template e não dispara rollout; o Pod continua rodando a imagem antiga. Para atualizar de fato, use uma tag nova ou kubectl rollout restart deployment/api-deployment -n daemon-lab, que injeta uma anotação no template e força a recriação.

O selector é imutável depois que o Deployment existe: mudar app: process-api para outro valor faz o apply falhar com “field is immutable”. A saída é criar outro Deployment e apagar o antigo — motivo pelo qual o label foi definido em contrato antes de escrever o YAML.

A pergunta que sempre vem

"Por que 50% e não 80%?" — Porque 50% dá margem para o pico antes de o Pod saturar; com 80%, o Pod já estaria quase no limite quando o HPA decidisse agir. E porque o alvo é percentual do request, não do limit.

14. O que os YAMLs não têm — e o que você responderia

Estes arquivos atendem ao edital, mas não estão prontos para produção. Saber exatamente o que falta — e o efeito de cada ausência — é o que separa "funciona na demo" de "entendi Kubernetes". A tabela abaixo é a sua resposta para "o que você melhoraria?".

AusenteConsequência hojeComo ficaria

livenessProbeuvicorn travado só é reiniciado se o processo morrer; se ele trava sem morrer, o Pod fica "vivo" e inútilhttpGet /health com failureThreshold; o kubelet reinicia o container

Exemplo de readiness/liveness que faria sentido — desde que exista a rota /health (não basta declarar a probe; apontar para /processes seria caro, porque ela itera 83 processos a cada verificação):

readinessProbe:
  httpGet:
    path: /health
    port: 8000
  initialDelaySeconds: 3
  periodSeconds: 5
livenessProbe:
  httpGet:
    path: /health
    port: 8000
  initialDelaySeconds: 10
  periodSeconds: 10
  failureThreshold: 3

E o volume do Nginx tem uma armadilha que quase ninguém percebe: montar um emptyDir em /usr/share/nginx/html esconde o index.html que veio na imagem, porque o volume sobrepõe o diretório. A correção é usar um initContainer que copie o HTML para o volume, ou montar o volume em um subdiretório e ajustar o root do Nginx para servir dali. Se você disser "só montar um emptyDir ali", a banca pode pedir para você abrir a página — e ela vai dar 404.

A resposta de 30 segundos para "o que falta?"

"Faltam probes, securityContext, recursos no Nginx e no cron, volume para os logs, PDB e NetworkPolicy. Nenhum era exigido pelo edital, mas eu sei o efeito de cada um: sem readiness o Service manda tráfego cedo; sem liveness um uvicorn travado não reinicia; sem recursos o Nginx é BestEffort; sem volume o log morre; sem PDB um drain derruba as duas réplicas; sem NetworkPolicy todo Pod alcança a API."
