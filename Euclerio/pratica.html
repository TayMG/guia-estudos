Antes de tudo: onde rodar

Tudo roda dentro do WSL2 (Ubuntu), não no PowerShell. O Docker Desktop precisa estar aberto e com a integração WSL habilitada (a baleia verde). Se o Docker não estiver de pé, o minikube start falha na primeira linha.

1.1 Criar e rodar a API local antes de containerizar (opcional, mas recomendado)

A criação da API são dois arquivos: api/requirements.txt (as três dependências com versão fixa) e api/main.py (imports, app = FastAPI(...) e as quatro rotas). O código completo, linha a linha, está em Código §1; aqui você só precisa da ordem: criar a pasta, instalar as dependências e subir o uvicorn. Antes de culpar o Docker ou o Kubernetes, prove que a API funciona no Python puro — é o que os prints APIrodandoTerminal.png e testesCurl.png mostram.

mkdir -p api && cd api
# crie requirements.txt e main.py (conteúdo em Código §1)
python3 -m venv .venv
source .venv/bin/activate          # no Windows: .venv\Scripts\activate
pip install -r requirements.txt
uvicorn main:app --reload --port 8000

Em outro terminal:

curl http://127.0.0.1:8000/processes
curl http://127.0.0.1:8000/processes/1
curl -X POST "http://127.0.0.1:8000/processes/start?command=sleep%2060"
curl -X DELETE "http://127.0.0.1:8000/processes/<PID>?force=true"

--reload é recurso de desenvolvimento: ele reinicia o processo quando o arquivo muda. Não vai para o container — em produção o código é imutável dentro da imagem. E 127.0.0.1 só funciona na sua máquina; dentro do container o uvicorn precisa de --host 0.0.0.0, como está no Dockerfile.

2. Buildar as três imagens

# a partir da raiz do repositório
cd api    && docker build -t process-api:latest .   && cd ..
cd nginx  && docker build -t nginx-cron:latest .    && cd ..
cd cron   && docker build -t cron-daemon:latest .   && cd ..

O que cada parte significa:

  • -t process-api:latest — nome e tag. O nome tem que ser idêntico ao do YAML, senão o Pod não encontra a imagem.
  • . — o contexto de build (a pasta enviada ao daemon). O Dockerfile é procurado ali.
  • cd .. no fim de cada linha — sem isso o segundo build rodaria na pasta errada.

Verificação:

docker images | grep -E "process-api|nginx-cron|cron-daemon"
Por que :latest e não uma versão

Porque os YAMLs usam process-api:latest e imagePullPolicy: Never. Se você trocar a tag na imagem e não no YAML, o Pod fica em ErrImageNeverPull. Em produção usar latest é má prática justamente por isso — não há rastreabilidade de versão.

2.1 Testar as três imagens no Docker (o “plano B” da demo)

Se o cluster falhar na apresentação, os containers ainda funcionam sozinhos. Testar localmente também prova que o problema, se aparecer, é de orquestração — não da imagem.

docker run -d --name api-teste    -p 8000:8000 process-api:latest
docker run -d --name nginx-teste  -p 8080:80   nginx-cron:latest
docker run -d --name cron-teste                 cron-daemon:latest

docker ps

curl http://127.0.0.1:8000/processes
curl http://127.0.0.1:8080/

# o log do cron do Nginx (o mesmo que o iframe mostra)
docker exec nginx-teste cat /usr/share/nginx/html/cron.txt

# o log do cron isolado
docker exec cron-teste cat /var/log/cron-task.log

# limpeza
docker rm -f api-teste nginx-teste cron-teste
ComandoO que ele ensina
-p 8000:8000porta do host : porta do container. Sem isso, o processo existe mas ninguém alcança
-p 8080:80por que 8080? A porta 80 do Windows/WSL pode estar ocupada ou exigir privilégio; mapear para 8080 evita conflito
docker exec ... cato log é arquivo, não stdout; docker logs não mostra o conteúdo do cron.txt
docker rm -fremove e para; sem -f, um container rodando não é removido

3. Entregar as imagens ao cluster

minikube start --driver=docker

minikube image load process-api:latest
minikube image load nginx-cron:latest
minikube image load cron-daemon:latest

Por que isso é necessário: o Minikube com driver Docker é um container separado, com um containerd próprio. A imagem que você construiu no WSL está no daemon do Docker Desktop, não dentro do nó. O image load copia a imagem para dentro do nó.

Sem esse passo, o kubelet tenta puxar de um registry, não encontra, e — como o YAML diz Never — o Pod entra em ErrImageNeverPull. É o erro número 1 de quem reproduz o projeto.

Alternativa: construir dentro do Minikube

eval $(minikube docker-env) aponta o cliente Docker para o daemon interno do nó; a partir daí, docker build já cria a imagem onde o kubelet vai procurá-la, e o image load deixa de ser necessário. O efeito dura só naquela sessão do terminal — abrir outro terminal e buildar de novo volta a usar o Docker Desktop. Por isso o projeto padronizou o minikube image load: é explícito e não depende de variável de ambiente.

4. Aplicar os YAMLs — a ordem importa

cd k8s

kubectl apply -f namespace.yaml        # 1º: todos os outros recursos referenciam este namespace
kubectl apply -f api-deployment.yaml
kubectl apply -f api-service.yaml
kubectl apply -f nginx-deployment.yaml
kubectl apply -f nginx-service.yaml
kubectl apply -f cron-deployment.yaml
kubectl apply -f hpa.yaml

O namespace vem primeiro porque os demais declaram namespace: daemon-lab. Se você aplicar um Deployment antes do namespace existir, o comando falha com namespaces "daemon-lab" not found.

Depois, esperar os Pods:

kubectl get pods -n daemon-lab
# aguarde todos em Running (ContainerCreating leva ~30 s)

Ativar as métricas — só depois disso o HPA funciona:

minikube addons enable metrics-server
kubectl apply -f hpa.yaml
kubectl get hpa -n daemon-lab      # pode levar 1–2 min para sair de <unknown>

5. Acessar a API e o Nginx

# opção 1 — túnel (recomendada no Windows)
minikube service api-service -n daemon-lab
minikube service nginx-service -n daemon-lab

# opção 2 — IP do nó (funciona dentro do WSL)
curl http://$(minikube ip):30080/processes
curl http://$(minikube ip):30081/

# opção 3 — port-forward (sem expor NodePort)
kubectl port-forward svc/api-service 8000:8000 -n daemon-lab

Com o túnel aberto, no navegador do Windows:

  • http://127.0.0.1:<porta>/docs — Swagger com os 4 endpoints
  • http://127.0.0.1:<porta>/processes — a lista de processos (83 no print)
Não feche o terminal do túnel

O minikube service fica em foreground mantendo o encaminhamento. Fechou o terminal, o site sai do ar — e o erro aparece como connection refused no navegador, o que assusta sem motivo.

6. Demonstrar self-healing

# 1. listar e copiar o nome de um Pod da API
kubectl get pods -n daemon-lab

# 2. deletar
kubectl delete pod api-deployment-7487485766-2chk4 -n daemon-lab

# 3. assistir a recriação
kubectl get pods -n daemon-lab -w

O que narrar enquanto acontece:

  1. "Deletei um Pod. O Deployment continua com replicas: 2."
  2. "O ReplicaSet controller percebe que só existe 1 Pod."
  3. "Ele cria outro a partir do mesmo template — nome diferente, mesmo label."
  4. "Em 9 segundos o novo está Running, e o Service já o inclui."
Se perguntarem "e se eu matar o container em vez do Pod?"

Aí é o kubelet que age: ele reinicia o container no mesmo Pod, conforme restartPolicy: Always. O nome do Pod não muda e a coluna RESTARTS aumenta. São dois mecanismos diferentes — saber separar isso é ponto garantido.

7. Demonstrar scaling

# terminal 1 — gerar carga (vai travar, é normal)
while true; do curl -s http://127.0.0.1:<PORTA>/processes > /dev/null; done

# terminal 2 — observar o HPA
kubectl get hpa -n daemon-lab -w

# terminal 3 — ver os Pods nascendo
kubectl get pods -n daemon-lab -w

O que esperar: TARGETS sobe de 2%/50% para 204%/50% e REPLICAS vai de 2 a 10 (respeitando maxReplicas). Ao parar a carga (Ctrl+C), a CPU cai a 2% e, após ~5 minutos, as réplicas voltam a 2.

Se o HPA não reagir

Cheque nesta ordem: (1) kubectl get hpa mostra <unknown>? → metrics-server não está pronto, espere 1–2 min; (2) TARGETS mostra valor mas não escala? → veja se o Deployment tem requests.cpu; (3) a carga está batendo no Pod certo? → confirme a porta do túnel.

8. Limpeza

# para a carga primeiro (Ctrl+C no terminal do while)

kubectl delete namespace daemon-lab   # apaga TODOS os recursos do projeto de uma vez
minikube stop                          # para o cluster, mantendo o estado
# minikube delete                      # apaga o cluster inteiro (irreversível)

Apagar o namespace é o jeito elegante: como todos os objetos estão nele, um comando remove Deployments, Services, HPA e Pods. É também a prova de que usar namespace foi uma boa decisão.

10. Diagnóstico: os comandos que respondem cada pergunta

Se algo der errado na demo, não importa o que você "acha": importa o que o cluster está dizendo. Estes são os comandos que você precisa saber de cor, e a pergunta que cada um responde.

ComandoPergunta que respondeO que olhar
kubectl get pods -n daemon-lab -o widequais Pods existem, em que nó e com qual IP?STATUS, READY, RESTARTS, NODE
kubectl describe pod <pod> -n daemon-labpor que este Pod não sobe?Events no fim: FailedScheduling, ErrImageNeverPull, Unhealthy
kubectl logs <pod> -n daemon-labo que o processo escreveu?stack trace do uvicorn, erro do nginx; -c <container> se houver mais de um
kubectl get events -n daemon-lab --sort-by=.lastTimestampo que aconteceu nos últimos minutos?ordem cronológica: agendamento, pull, probe, kill
kubectl get endpoints -n daemon-labo Service tem para onde mandar tráfego?lista de IPs: vazia = selector errado ou Pod não Ready

kubectl top pod -n daemon-labquanto cada Pod consome agora?CPU em milicores; é a mesma fonte que o HPA lê

A frase que salva a demo

"O Pod está em Pending; antes de mexer, vou olhar os eventos com kubectl describe para saber se é recurso, imagem ou agendamento." Isso mostra método. O que derruba é ficar reiniciando o cluster sem ler o evento.

Detalhe de idempotência: aplicar o hpa.yaml duas vezes (uma antes e outra depois do metrics-server) não cria duplicata — kubectl apply reconcilia o mesmo objeto. O que não se deve fazer é reaplicar o Deployment da API com o HPA em 10: o manifesto declara replicas: 2 e o HPA reescala em seguida, gerando uma disputa declarativa.
