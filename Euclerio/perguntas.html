06 · Treino de banca

Perguntas e respostas

Clique em cada pergunta. A resposta curta é o que você diz em 30 segundos; o resto é o que você usa se ele insistir. Treine falando em voz alta — ler não é o mesmo que responder.

Regra de ouro

Responda em uma frase e pare. Quem fala demais entrega fragilidade. Se a banca quiser mais, ela pergunta — e aí você tem o aprofundamento pronto.

Se ele for além do básico

Esta página cobre o que costuma cair. Para as perguntas de mecanismo, número e contrafactual — “por que o HPA subiu em degraus?”, “quem é o PID 1 do Nginx?”, “o que muda sem hostPID?” — use a Banca difícil.

As 10 que ele vai perguntar

1. O que é um daemon e por que os três serviços do trabalho são daemons?

Resposta curta: "Daemon é um processo de longa duração, sem terminal, que roda em segundo plano esperando eventos. O Nginx espera conexões, o crond espera o minuto virar, e a API espera requisições HTTP — os três vivem até serem parados e escrevem log."

Se insistir: no container, o daemon não pode se desprender (double fork), senão o PID 1 morre e o container termina. Por isso usamos nginx -g "daemon off;" e crond -f — foreground obrigatório.

2. Qual é a diferença entre container e máquina virtual?

Resposta curta: "Container compartilha o kernel do host e isola processos com namespaces e cgroups; VM tem kernel próprio, virtualizado por hypervisor. Por isso container sobe em milissegundos e VM em dezenas de segundos — e por isso o isolamento do container é mais fraco."

Se insistir: três componentes fazem o container: namespace (o que ele vê), cgroup (quanto ele pode usar) e um sistema de arquivos próprio via overlayfs. Não há emulação de hardware.

3. O que é um Pod e por que ele existe?

Resposta curta: "Pod é a menor unidade do Kubernetes: um ou mais containers que compartilham rede e IPC. Todos têm o mesmo IP, então não podem usar a mesma porta. Existe porque às vezes dois processos precisam estar na mesma rede — um sidecar, por exemplo."

Se insistir: todo Pod tem um container pause invisível que segura os namespaces de rede. É ele que aparece na listagem de processos do hostPID_kubernete.png.

4. O que é um Deployment e por que não criar Pods direto?

Resposta curta: "Deployment declara o estado desejado — imagem, réplicas, recursos — e cria um ReplicaSet que garante esse número. Pod solto não é recriado se morrer; o Deployment traz réplicas, rolling update e rollback."

Se insistir: o nome esquisito do Pod (api-deployment-7487485766-2chk4) é deployment + hash do template + sufixo aleatório. O hash é como o Deployment sabe quais Pods são dele.

5. Como funciona o self-healing de vocês?

Resposta curta: "Em dois níveis. Se o container morre, o kubelet reinicia no mesmo Pod. Se o Pod é deletado, o ReplicaSet controller vê que tem 1 de 2 e cria outro — foi o que o print mostra, em 9 segundos."

Se insistir: é o loop de reconciliação normal, não um evento especial: estado desejado 2, estado atual 1, aja. Quem age é o controller-manager, não o kubelet.

6. Como o HPA decide escalar?

Resposta curta: "Ele lê o uso médio de CPU de cada Pod a cada ~15 segundos, divide pelo request e compara com o alvo. A fórmula é ceil(réplicas × atual / alvo). Com 204% de 50%, dá 9."

Se insistir: precisa de requests.cpu (senão é <unknown>), do metrics-server, e tem tolerância de 10% para não oscilar. Scale-up é imediato; scale-down espera 5 minutos.

7. O que é hostPID e por que vocês usaram?

Resposta curta: "É compartilhar o namespace de PID do nó com o Pod. Sem ele, a API veria só os processos do próprio container. Com ele, o /processes lista os 83 processos do nó, incluindo kubelet e etcd — é a prova do print."

Se insistir: é decisão central do projeto: o edital pede uma API que gerencie processos em execução, e sem hostPID ela só gerenciaria a si mesma.

8. Por que NodePort e não LoadBalancer?

Resposta curta: "LoadBalancer depende de um provedor de nuvem para dar IP externo; no Minikube local isso exigiria MetalLB. NodePort resolve com uma porta alta no nó — 30080 para a API e 30081 para o Nginx."

9. Como vocês garantem que o Service encontra os Pods?

Resposta curta: "Por label. O template do Deployment põe app: process-api, e o selector do Service procura esse mesmo label. Se divergir, o Service fica sem endpoints e o curl dá connection refused."

10. O que acontece se um Pod morrer durante a apresentação?

Resposta curta: "O ReplicaSet recria em segundos e o Service continua atendendo pelo outro Pod. É exatamente o que vamos demonstrar agora." (E aí você demonstra o self-healing ao vivo.)

API e processos

O que a API faz, em uma frase?

"Expõe por HTTP quatro operações sobre processos do sistema: listar, inspecionar por PID, iniciar e encerrar — usando psutil para ler o /proc e Popen para criar processos."

Por que FastAPI e não Flask?

"Validação automática pelos type hints e Swagger gerado em /docs sem escrever documentação. Para quatro rotas, o ganho é justamente a documentação — que virou evidência do trabalho."

Como o psutil lê os processos?

"No Linux ele lê o /proc, que é um sistema de arquivos virtual gerado pelo kernel. Cada processo tem uma pasta /proc/<pid> com status, cmdline e fd. Não precisa de root para listar, mas precisa para detalhes de processos de outro usuário — daí o 403."

Qual a diferença entre SIGTERM e SIGKILL?

"SIGTERM (15) é um pedido educado: o processo pode capturar, salvar estado e sair. SIGKILL (9) é o kernel matando, sem chance de reação. Por isso o endpoint usa terminate() por padrão e kill() só com force=true."

Se insistir: é a mesma lógica do Kubernetes ao encerrar um Pod — SIGTERM, espera o gracePeriod (30 s), depois SIGKILL.

Por que usar Popen e não os.system?

"os.system bloqueia até o comando terminar e não devolve PID — sem PID, não dá para inspecionar nem encerrar. O Popen dispara em background e devolve o PID na hora, que é o que permite o ciclo iniciar → inspecionar → encerrar."

Por que não usar shell=True?

"Porque sem shell não há interpretação de ;, | e &&. Um comando malicioso vira argumento literal em vez de segundo comando. O custo é não aceitar pipes nem aspas — para isso existiria o shlex.split."

Por que cpu_percent retorna 0.0 na primeira chamada?

"Porque o psutil calcula CPU por diferença entre duas leituras. Na primeira não há leitura anterior, então ele retorna 0.0. É comportamento da biblioteca, não bug — a segunda chamada já traz o valor real."

O que acontece com os processos que a API iniciou quando o Pod reinicia?

"Eles morrem junto. Com hostPID, o processo nasce no namespace de PID do nó, mas continua dentro do cgroup do container — quando o container é encerrado, o runtime mata tudo do cgroup. Não sobra processo órfão."

Se insistir: é uma limitação real de escopo: o projeto gerencia processos, não persiste estado deles. Um gerenciador de verdade usaria systemd-run ou um supervisor fora do container.

Docker

Diferença entre imagem e container

"Imagem é o pacote imutável — camadas de sistema de arquivos + metadados. Container é uma instância em execução dela, com uma camada gravável no topo. Uma imagem pode gerar dez containers."

O que é uma camada e por que a ordem do Dockerfile importa?

"Cada instrução gera uma camada read-only, cacheada e compartilhada entre imagens. Se eu copiar o main.py antes do pip install, qualquer mudança no código invalida a instalação. Copiando o requirements.txt primeiro, só a dependência invalida — o build fica rápido."

Por que python:3.11-slim?

"Imagem oficial enxuta, ~120 MB em vez de ~1 GB da completa. Não precisamos de compilador porque o psutil e o FastAPI vêm em wheel. Menos superfície de ataque e build mais rápido."

EXPOSE abre a porta?

"Não. EXPOSE é documentação — metadado da imagem. Quem publica é docker run -p ou, no Kubernetes, o containerPort combinado com o Service."

Por que imagePullPolicy: Never?

"Porque as imagens foram construídas localmente e carregadas no nó com minikube image load; elas não existem em registry nenhum. Com Never, o kubelet não tenta baixar — se a imagem não estiver lá, o Pod fica em ErrImageNeverPull, que é um erro claro."

O que é containerd? E runc?

"containerd é o runtime de alto nível: gerencia imagens e ciclo de vida, e é o que o Kubernetes usa via CRI. runc é o de baixo nível: chama clone()/unshare(), monta o sistema de arquivos e inicia o processo. Docker é a camada de conveniência em cima disso."

Kubernetes

O que é o etcd?

"Banco chave-valor distribuído que guarda todo o estado do cluster. Todo objeto — Pod, Service, HPA — é um registro nele. Se o etcd se perde, o cluster perde o estado; é por isso que ele é o componente mais crítico do control plane."

O que faz o kubelet?

"É o agente do nó. Ele observa a API, vê os Pods destinados ao seu nó e garante que os containers rodem conforme a especificação — inclusive reiniciando container morto e reportando status. Ele não decide nada: só executa o que o control plane determinou."

O que faz o scheduler?

"Escolhe em qual nó cada Pod novo vai rodar, com base em recursos disponíveis, afinidade e taints/tolerations. Só decide; quem executa é o kubelet."

O que é o loop de reconciliação?

"O padrão central do Kubernetes: você declara o estado desejado, um controlador compara com o estado atual e age para igualá-los, continuamente. Self-healing e HPA são esse mesmo loop aplicado a réplicas."

O que é um ReplicaSet?

"Controlador que garante N Pods com determinado label. O Deployment cria e gerencia ReplicaSets — um por versão do template —, o que permite rolling update e rollback."

Namespace do Kubernetes é a mesma coisa que namespace do Linux?

"Não. O do Linux isola recursos do kernel (PID, rede, mount) e é o que o container usa. O do Kubernetes é uma divisão lógica de objetos dentro do cluster — o nosso é daemon-lab."

O que é o container pause?

"Um container mínimo que segura os namespaces de rede e IPC do Pod. Os containers reais entram nesses namespaces, e é por isso que todos compartilham IP e porta. Ele aparece na listagem do hostPID."

O que faz o kube-proxy?

"Mantém no nó as regras de rede (iptables ou IPVS) que traduzem o IP virtual do Service para um Pod real. É ele que faz o NodePort 30080 chegar na porta 8000 de um Pod."

Por que minikube service abre um túnel?

"Porque com driver Docker o nó tem IP 192.168.49.2, que vive numa rede interna do Docker e não é roteável a partir do Windows. O comando cria um encaminhamento de porta local para o nó — e por isso o terminal precisa ficar aberto."

Por que o cron tem 1 réplica e a API tem 2?

"Porque o crond não tem coordenação entre instâncias: duas réplicas executariam a mesma tarefa agendada em duplicidade. A API é stateless, então pode ter quantas forem."

HPA e escalonamento

Qual é a fórmula do HPA?

"réplicasDesejadas = ceil(réplicasAtuais × métricaAtual / métricaAlvo). Com 2 réplicas e 204% contra alvo de 50%: ceil(2 × 204/50) = 9 — e o print mostra 9 antes de chegar a 10, que é o máximo."

O que significa 204%?

"É uso relativo ao request: cada Pod usa em média ~204 milicores, contra um request de 100m. Não é 204% da máquina."

O que o HPA exige do Deployment?

"resources.requests.cpu declarado. A métrica de utilização é percentual do request; sem ele o divisor não existe e o HPA mostra <unknown>."

Diferença entre HPA, VPA e Cluster Autoscaler

"HPA muda o número de Pods (horizontal). VPA muda CPU/memória de cada Pod (vertical). Cluster Autoscaler adiciona nós quando não há onde caber o Pod. Usamos só HPA."

Por que demora ~5 minutos para descer?

"Porque o HPA tem uma janela de estabilização padrão de 300 segundos para scale-down, para não ficar subindo e descendo a cada oscilação. Scale-up é imediato."

Segurança (a seção que mais tira ponto)

hostPID: true não é perigoso?

Resposta curta: "É, e é uma decisão consciente. Sem hostPID a API não vê o sistema operacional, e o trabalho perde o sentido. Em produção isso viria com controle de acesso, rede restrita e allowlist de PIDs."

Se insistir: com hostPID o Pod enxerga e pode sinalizar qualquer processo do nó — inclusive kubelet e etcd.

Como vocês protegeriam isso em produção?

Resposta correta (decorar): "Primeiro, tiraria o NodePort: com ClusterIP + port-forward a API deixa de ser alcançável pela rede. Segundo, NetworkPolicy restringindo origens. Terceiro, autenticação na própria API (token ou mTLS). Quarto, allowlist de PIDs e sinais em vez de kill arbitrário. E, como hostPID viola o Pod Security Standard baseline, o Pod precisaria de um namespace privilegiado com política explícita."

Não diga "RBAC"

RBAC controla quem pode chamar o kube-apiserver — não quem chama a sua API HTTP na porta 30080. Dizer "RBAC resolve" é a resposta errada mais comum e demonstra que o conceito não foi entendido.

Por que não tem autenticação na API?

"Porque o escopo era demonstrar gerenciamento de processos em um cluster local de estudo. Autenticação não era exigida pelo edital e adicionaria complexidade sem mudar o que precisávamos provar. Está registrada como limitação."

O que é o Pod Security Standard?

"São perfis de segurança do Kubernetes — privileged, baseline e restricted. O baseline proíbe host namespaces, então um Pod com hostPID: true seria rejeitado num cluster com a política aplicada. O Minikube, por padrão, não aplica."

Um container roda como root. Isso é problema?

"Sim, é o padrão de várias imagens e o nosso caso. A mitigação é runAsNonRoot, readOnlyRootFilesystem e capabilities mínimas. Mas, com hostPID, rodar como root é ainda mais sensível, porque o alcance sobre os processos do nó aumenta."

Perguntas-pega

Se eu rodar kubectl delete deployment api-deployment, o que acontece?

"O Deployment e o ReplicaSet dele são removidos, os Pods da API somem e o Service fica sem endpoints — o curl passa a falhar. O self-healing não atua nesse caso: nada recria um Deployment removido. Para voltar, é kubectl apply -f api-deployment.yaml."

Se eu matar o container da API com kill -9, o Pod é recriado?

"O container é reiniciado no mesmo Pod pelo kubelet, por causa do restartPolicy: Always. O nome do Pod não muda; a coluna RESTARTS aumenta. Pod novo só acontece se o Pod for deletado."

E se eu apagar o namespace?

"Todos os objetos dele somem — Deployments, Services, HPA e Pods. É o nosso comando de limpeza, justamente porque o namespace agrupa tudo."

O HPA mostrando <unknown> é bug?

"Não: significa que o metrics-server ainda não entregou métricas. Leva 1–2 minutos depois de ativar o addon. Se persistir, o metrics-server não está rodando."

Com 2 réplicas do Nginx, os dois escrevem no mesmo cron.txt?

"Não. Cada Pod tem seu próprio sistema de arquivos efêmero, então cada um escreve o seu cron.txt. O Service escolhe qual Pod responde, então o log pode variar a cada requisição. Para compartilhar, precisaria de um volume."

Por que o Pod mostra 2/2 na coluna READY?

"Porque o Pod tem dois containers e os dois estão prontos. No nosso caso, os Pods mostram 1/1 — um container cada. O pause não conta como container do Pod."

Por que não usaram DaemonSet?

"DaemonSet garante um Pod por nó — faz sentido para agente de log ou monitoramento. Nosso caso é serviço com réplicas, então Deployment é o objeto certo. DaemonSet seria a escolha se quiséssemos coletar processos de todos os nós."

E StatefulSet?

"StatefulSet dá identidade estável e volume por réplica — para banco de dados. Nossos serviços são stateless (API e Nginx) e o cron é único, então não há necessidade de identidade nem de persistência."

Por que não usaram Docker Compose?

"Porque o edital exige Kubernetes e as demonstrações de self-healing e scaling. Compose roda containers em um host, mas não reconcilia estado nem escala automaticamente."

O que aconteceria se o nó caísse?

"Com Minikube de um nó só, o cluster inteiro cairia. Num cluster multi-nó, o control plane recriaria os Pods nos nós restantes. Não demonstramos isso porque não havia segundo nó — é uma limitação honesta do ambiente."

Como vocês provam que é hostPID e não apenas o container?

"Porque a lista traz processos que não existem dentro do container: kube-apiserver, etcd, kubelet, kube-proxy, os pause dos outros Pods — e até os nginx e crond dos outros containers do mesmo nó. Sem hostPID, a API veria só o uvicorn e seus filhos — 3 ou 4 processos, não 83."

Se eu fizer kubectl scale deployment api-deployment --replicas=5, o HPA desfaz?

"Sim, na próxima leitura. O HPA é o dono do campo replicas enquanto estiver ativo; ele recalcula e sobrescreve. Para escalar manualmente de forma estável, seria preciso pausar ou remover o HPA."

O que é Ingress e por que não usaram?

"Ingress é uma camada HTTP que roteia por host e caminho, com TLS, na frente dos Services. Não usamos porque exigiria um ingress controller e não era necessário para demonstrar os três daemons; o NodePort resolveu o acesso."

Como vocês saberiam que o problema é DNS e não o Service?

"Testando por IP do Pod (kubectl get endpoints) e por nome. Se funciona por IP e falha por nome, é DNS (CoreDNS). Se falha nos dois, é selector ou Pod não pronto."

Extras que a banca pode puxar

O que são liveness e readiness probes?

"São verificações periódicas do kubelet. A liveness pergunta se o container está vivo — se falha, o container é reiniciado. A readiness pergunta se ele está pronto para receber tráfego — se falha, o Pod sai dos endpoints do Service, sem reiniciar. O projeto não tem nenhuma das duas; seria o primeiro item de melhoria."

Quem escalona o quê: SO, kube-scheduler ou HPA?

"Três níveis. O escalonador do SO decide qual thread usa a CPU e por quanto tempo (quantum, preempção). O kube-scheduler decide em qual nó cada Pod roda, uma vez. O HPA decide quantas réplicas existem. O projeto usa os três."

O que é OOMKilled?

"É o kernel matando um processo que estourou o limite de memória do cgroup. Não é decisão do Kubernetes. Como o projeto só declara limits.cpu e nenhum limite de memória, não há risco de OOMKilled — o Pod da API é Burstable e, sob disputa de CPU, é estrangulado, não morto."

O que é QoS e qual é a classe dos nossos Pods?

"Qualidade de serviço: Guaranteed (requests = limits), Burstable (tem requests, mas não é Guaranteed) e BestEffort (nada declarado). Os Pods da API são Burstable, porque declaram 100m de request e 500m de limite de CPU, sem memória. Já Nginx e cron não declaram nada e são BestEffort — são os primeiros despejados sob pressão. Sob pressão, o kubelet despeja primeiro os BestEffort."

Por que o log do cron não sobrevive a um restart?

"Porque não há volume: o cron.txt está na camada gravável do container, que é descartada quando ele é recriado. Um emptyDir sobreviveria ao restart do container; um PVC sobreviveria também à recriação do Pod. E, com duas réplicas do Nginx, cada uma tem seu próprio arquivo — o emptyDir não compartilha entre Pods."

Por que não usar um CronJob do Kubernetes no lugar do cron-deployment?

"Porque o objetivo era demonstrar um daemon de agendamento dentro do container. O CronJob cria um Pod novo a cada execução e termina; não há daemon permanente para mostrar. Em produção, o CronJob seria a escolha correta — com concurrencyPolicy: Forbid, backoffLimit e limites de histórico."

O RBAC impede a API de matar processos do nó?

"Não. RBAC controla o que a identidade pode fazer no kube-apiserver. O kill da API é uma syscall direta no kernel; quem permite é o UID 0 + CAP_KILL + o namespace de PID compartilhado pelo hostPID. A mitigação é reduzir exposição (ClusterIP + port-forward), autenticar, criar allowlist de PIDs e isolar o Pod em um namespace privilegiado documentado."

O que falta nos YAMLs para produção?

"Probes de readiness e liveness (com uma rota /health), securityContext, recursos no Nginx e no cron (hoje são BestEffort), volume para os logs, PodDisruptionBudget, NetworkPolicy e uma estratégia de rollout explícita. Nenhum era exigido pelo edital, mas cada um tem um efeito concreto — eu sei qual."

Como responder "não sei"

A fórmula em três partes

1. Reconheça: "Isso eu não sei de cabeça."
2. Mostre o caminho: "Mas eu investigaria assim: comando/ferramenta."
3. Volte ao que domina: "O que eu sei é que fato relacionado."

Isso vale mais que uma resposta errada dita com confiança. Banca não desconta honestidade; desconta invenção.
