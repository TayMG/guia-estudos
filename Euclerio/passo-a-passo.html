Como o trabalho foi feito — do zero e sem pressa

Esta é a página para quem nunca viu Linux, Docker ou Kubernetes na vida. Ela conta o trabalho na ordem em que ele foi construído: para que serve cada peça, o que o grupo fez, qual arquivo foi criado, o que tem dentro dele e como saber que funcionou.

Como ler esta página

Cada passo tem sempre os mesmos cinco blocos: para que serve · o que o grupo fez · arquivo criado · como saber que funcionou · se te perguntarem. Se você ler os 12 passos na ordem, no fim vai conseguir contar o trabalho inteiro em voz alta.

Se você está com pressa

Vá direto para A história em 12 passos e depois para As 8 frases que resumem tudo. Em 10 minutos você tem o esqueleto. O resto da página é o detalhe que a banca cobra.

2. O problema que o trabalho resolve

Hoje um sistema grande não roda numa máquina só: ele é dividido em vários pedacinhos espalhados. Isso cria três dores:

  1. Não dá para ver o que está acontecendo. Se o problema está em outra máquina, como saber qual processo está comendo a CPU?
  2. Quando algo cai, alguém precisa levantar. Sem automação, é gente abrindo terminal de madrugada.
  3. Pico de acesso custa caro. Ou você compra máquina demais e desperdiça, ou de menos e o site cai.

O trabalho ataca as três: uma API que mostra e controla processos do sistema operacional, um orquestrador (Kubernetes) que recria o que cai, e um escalonador automático (HPA) que cria cópias quando a carga sobe. Tudo com três daemons diferentes, que é o que o edital pede.

O edital pediuO que o grupo entregou
Mínimo de 3 containers com daemons diferentesAPI (uvicorn), Nginx (nginx) e cron isolado (crond). O container do Nginx roda dois daemons: nginx + crond.

Deploy orquestrado pelo Kubernetes3 Deployments, 5 Pods, 2 Services e 1 HPA, tudo no namespace daemon-lab
Demonstrar self-healingPod apagado e recriado automaticamente em 9 s, com print

Passo 1 — Combinar quem faz o quê e com que nomes

Para que serve: o trabalho tem partes feitas por pessoas diferentes (API, containers, Kubernetes, documentação). Se cada um inventar um nome de imagem ou uma porta, as partes não se encaixam no fim.

O que o grupo fez: escreveu um "contrato" antes de codar. Ficou decidido: imagens com nome exato (process-api:latest, nginx-cron:latest, cron-daemon:latest), portas internas 8000 (API) e 80 (Nginx), NodePorts 30080 e 30081, namespace daemon-lab e as etiquetas app: process-api, app: nginx e app: cron.

Arquivo criado: docs/interfaces.md (o contrato) e docs/tarefas.md (quem faz o quê).

Como saber que funcionou: os 7 YAMLs usam exatamente esses nomes. Se um nome estivesse diferente, o Pod ficaria em ImagePullBackOff — e foi justamente isso que o contrato evitou.

Se te perguntarem "por que um contrato?": porque Kubernetes não adivinha. Ele procura a imagem pelo nome escrito no YAML. Nome diferente = imagem não encontrada.

Passo 2 — Escrever a API que fala com os processos

Para que serve: é o "balcão de atendimento" do trabalho. O edital pede quatro operações: listar, inspecionar, iniciar e encerrar processos.

Pense assim: o sistema operacional tem uma lista de funcionários (processos) trabalhando. A API é a recepcionista que consulta essa lista pra você, sem você precisar entrar na sala.

O que o grupo fez: criou dois arquivos.

  • requirements.txt — a lista de bibliotecas, com versão travada: fastapi==0.104.1, uvicorn==0.24.0, psutil==5.9.6.
  • main.py — o código: cria o app e declara as 4 rotas.

As quatro rotas, em português:

RotaO que ela fazFerramenta usada
GET /processes"me mostra todos os processos que estão rodando"psutil.process_iter
GET /processes/{pid}"me mostra os detalhes do processo de crachá número X"psutil.Process(pid)
POST /processes/start?command=..."começa a rodar este comando pra mim"subprocess.Popen
DELETE /processes/{pid}?force=true"encerra o processo X" (educado, ou à força)proc.terminate() / proc.kill()

O miolo de cada rota é pequeno. A de listar, por exemplo, é só isto:

@app.get("/processes")
def list_processes():
    processes = []
    for proc in psutil.process_iter(['pid', 'name', 'username', 'status']):
        processes.append(proc.info)
    return {"total": len(processes), "processes": processes}

Como saber que funcionou: antes de colocar em container, o grupo subiu a API no Python puro (uvicorn main:app --reload --port 8000) e testou com curl. Os prints APIrodandoTerminal.png e testesCurl.png são exatamente essa prova: se a API falhasse ali, o problema era o código, não o Docker.

Se te perguntarem "por que psutil e não o comando ps?": porque o ps devolve texto, e você teria que ficar cortando pedaços de texto. O psutil lê direto a pasta /proc do Linux e entrega os dados organizados em Python.

E "por que Popen?": porque ele inicia o processo e devolve o PID na hora, sem prender a requisição esperando o comando terminar.

Passo 3 — Empacotar a API numa imagem

Para que serve: a API precisa rodar igual em qualquer máquina. A imagem cola o código + o Python + as bibliotecas num pacote fechado. Aí não existe "na minha máquina funciona".

Pense assim: a imagem é a marmita já montada e lacrada. O container é a marmita aberta e sendo comida.

Arquivo criado: api/Dockerfile. Cada linha tem um motivo:

# 1. começa de uma imagem oficial que já tem Python 3.11 (versão enxuta)
FROM python:3.11-slim
# 2. define a pasta de trabalho dentro do container
WORKDIR /app
# 3. copia só a lista de bibliotecas primeiro (para o cache funcionar)
COPY requirements.txt .
# 4. instala as bibliotecas sem guardar cache de download
RUN pip install --no-cache-dir -r requirements.txt
# 5. agora sim copia o código
COPY main.py .
# 6. documenta que a API escuta na 8000 (não abre a porta sozinho)
EXPOSE 8000
# 7. o comando que roda quando o container sobe
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]

Por que --host 0.0.0.0 e não 127.0.0.1: o 127.0.0.1 significa "só aceito conexão de dentro da minha própria casa". Dentro do container, quem chama a API é o Service, que vem de fora — então a API tem que escutar em todas as interfaces (0.0.0.0).

Por que copiar requirements.txt antes de main.py: o Docker guarda o resultado de cada linha. Se só o código mudou, ele reaproveita a instalação das bibliotecas e o build fica rápido.

Como saber que funcionou: docker build -t process-api:latest . e depois docker run -p 8000:8000 process-api:latest. O print imagemDocker.png mostra a imagem criada.

Se te perguntarem "por que slim?": porque a imagem completa do Python traz compilador e ferramentas que não são usadas em produção. A slim é menor, sobe mais rápido e tem menos coisa para dar errado.

Passo 4 — Montar o daemon de rede (Nginx)

Para que serve: o edital pede daemons. Nginx é o exemplo clássico de daemon de rede: ele fica ligado o tempo todo, escutando a porta 80, e responde quando alguém pede uma página.

Pense assim: se a API é a recepcionista, o Nginx é o letreiro da loja: qualquer um que chegue vê a página e sabe que o serviço está no ar.

O que o grupo fez: partiu da imagem oficial nginx:alpine (Alpine é uma distribuição Linux minúscula, ótima para container) e copiou uma página HTML para a pasta pública do servidor.

Arquivos criados: nginx/Dockerfile (começo) e nginx/html/index.html.

A página é simples de propósito: um título, um aviso de que o servidor está no ar e um iframe que exibe o arquivo cron.txt — a "prova visível" de que o cron está trabalhando.

<iframe src="cron.txt" title="Log do Cron"></iframe>

Como saber que funcionou: docker run -p 8080:80 nginx-cron:latest e abrir http://localhost:8080. Os prints verificandoDockerNginx.png, teste-conteinerNginx.png e sitedemostracao.png mostram essa etapa, ainda no Docker puro.

Se te perguntarem "o que é um daemon?": é um processo que roda em segundo plano, sem terminal e sem ninguém digitando nada, normalmente esperando um evento (uma conexão, um horário). O Nginx espera conexões; o cron espera o relógio.

Passo 5 — Colocar um cron dentro do Nginx

Para que serve: provar que um mesmo container pode ter mais de um daemon trabalhando junto — e gerar uma atividade contínua (o log a cada minuto) que a banca consegue ver.

O que o grupo fez: escreveu um pequeno script de entrada que sobe dois programas: o cron em segundo plano e o Nginx em primeiro plano.

Arquivo criado: nginx/Dockerfile (o restante).

# cria o script /entrypoint.sh com duas linhas:
#   busybox crond -b -l 8 -c /etc/crontabs   → sobe o cron em segundo plano
#   nginx -g "daemon off;"                   → sobe o Nginx em primeiro plano
RUN echo '#!/bin/sh' > /entrypoint.sh && \
    echo 'busybox crond -b -l 8 -c /etc/crontabs' >> /entrypoint.sh && \
    echo 'nginx -g "daemon off;"' >> /entrypoint.sh && \
    chmod +x /entrypoint.sh

# a tarefa agendada: a cada minuto, grava a data no arquivo público
RUN echo "* * * * * date >> /usr/share/nginx/html/cron.txt" > /etc/crontabs/root

# copia a página HTML para a pasta pública do Nginx
COPY html /usr/share/nginx/html

# o container começa rodando o script
CMD ["/entrypoint.sh"]
DetalhePor que está assim
* * * * *são cinco campos (minuto, hora, dia, mês, dia da semana). Cinco asteriscos = "todo minuto de todo dia".
date >> cron.txtdate imprime a data/hora; >> acrescenta no fim do arquivo, sem apagar o que já estava lá.
cron.txt na pasta do Nginxporque essa pasta é pública: o navegador consegue baixar o arquivo direto, sem a API no meio.
crond -b-b = background. O cron não pode ser o "dono" do container aqui, porque o dono é o Nginx.
nginx -g "daemon off;"por padrão o Nginx se manda para segundo plano e "solta" o terminal. Em container isso faria o container morrer. daemon off obriga o Nginx a ficar em primeiro plano.
-l 8nível de log do cron (quanto detalhe ele registra).

Como saber que funcionou: abrir a página e ver as linhas de data aparecendo dentro do quadro. O print cronNginxfuncionando.png é essa prova.

Detalhe que a banca pode cobrar: o arquivo é atualizado a cada minuto, mas o iframe não se recarrega sozinho. Para ver as linhas novas é preciso atualizar a página. O slide diz "atualiza em tempo real" no sentido de que o log é contínuo — se perguntarem, explique essa diferença com tranquilidade.

Passo 6 — Criar o cron isolado

Para que serve: completar os três containers com daemons diferentes. Aqui o cron é o único morador, então ele pode ser o processo principal.

Arquivo criado: cron/Dockerfile — o menor do projeto, com 5 linhas.

FROM alpine:latest

# a cada minuto, grava a data num arquivo de log
RUN echo "* * * * * date >> /var/log/cron-task.log" > /etc/crontabs/root

# roda o cron em PRIMEIRO plano (-f), porque aqui ele é o único processo
CMD ["busybox", "crond", "-f", "-l", "8", "-c", "/etc/crontabs"]

A diferença que importa: no Nginx o cron usou -b (segundo plano) porque o Nginx era o dono do container. Aqui o cron usa -f (primeiro plano) porque ele é o dono. Errar isso faz o container morrer sozinho.

Como saber que funcionou: o log fica dentro do container, num arquivo. Para ver: docker exec <container> cat /var/log/cron-task.log. No Kubernetes é o mesmo raciocínio, com kubectl exec — kubectl logs mostra as mensagens do próprio cron, não as linhas de data.

Se te perguntarem "por que só 1 réplica?": porque dois crons fariam a mesma tarefa duas vezes. A API e o Nginx têm 2 réplicas para dar disponibilidade; o cron, não.

Passo 7 — Preparar o cluster e carregar as imagens

Para que serve: até aqui tudo rodou no Docker "solto". Agora entra o orquestrador: ele decide onde cada container roda, recria o que cai e escala o que enche.

Pense assim: o Docker sozinho é um cozinheiro. O Kubernetes é o gerente do restaurante inteiro.

O que o grupo fez: subiu o Minikube (Kubernetes de uma máquina só) usando o Docker como motor, e carregou as três imagens para dentro do nó.

# 1. sobe o cluster local
minikube start --driver=docker

# 2. leva as imagens construídas na sua máquina para dentro do nó
minikube image load process-api:latest
minikube image load nginx-cron:latest
minikube image load cron-daemon:latest

Por que o image load é obrigatório: essas imagens não existem no Docker Hub — foram construídas na máquina do grupo. E os YAMLs dizem imagePullPolicy: Never, ou seja, "não tente baixar; use o que já está aqui". Sem o load, o Pod fica travado em ErrImageNeverPull.

Como saber que funcionou: kubectl get nodes mostra o nó como Ready, e minikube image ls lista as três imagens.

Passo 8 — Escrever os 7 YAMLs

YAML é a "lista de pedidos" do Kubernetes: você descreve o que quer e ele faz. São sete arquivos, cada um com uma responsabilidade. Esta tabela é o coração do passo:

ArquivoO que ele criaO que tem dentro (e por quê)

k8s/nginx-deployment.yaml2 Pods do Nginxreplicas: 2, imagem nginx-cron, porta 80.

Os campos que a banca vai pedir para explicar

CampoEm português
replicas: 2"quero sempre 2 cópias rodando". Se uma cair, o Kubernetes repõe.
selector.matchLabels + template.labelsa etiqueta do Pod e o ímã que o Service usa para encontrá-lo. Precisam ser iguais, senão o Service não acha ninguém.
hostPID: true"deixe este Pod ver os processos do nó inteiro", não só os dele. É o que dá sentido à API.
imagePullPolicy: Never"não baixe imagem, use a que está no nó". Obrigatório aqui, porque as imagens são locais.
requests.cpu: 100m"reserve 0,1 núcleo para este Pod". O HPA calcula a porcentagem em cima disso.
limits.cpu: 500m"nunca deixe passar de 0,5 núcleo". É o teto.
nodePort: 30080a porta aberta na fachada do nó, para você acessar de fora do cluster.
averageUtilization: 50"quero a média de CPU em 50% do que foi reservado". Acima disso, ele cria mais réplicas.

Um pedaço do api-deployment.yaml para você ver o formato:

spec:
  replicas: 2
  selector:
    matchLabels:
      app: process-api
  template:
    metadata:
      labels:
        app: process-api
    spec:
      hostPID: true
      containers:
      - name: api
        image: process-api:latest
        imagePullPolicy: Never

Como saber que funcionou: kubectl apply --dry-run=client -f arquivo.yaml valida o texto sem criar nada. Depois do apply, kubectl get pods -n daemon-lab mostra os Pods nascendo.

Se te perguntarem "por que 2 réplicas de API e Nginx?": disponibilidade — se uma cair, a outra atende, e o Service divide as requisições entre as duas.

Passo 9 — Aplicar e conferir

A ordem importa: o namespace precisa existir antes de qualquer coisa morar nele.

kubectl apply -f k8s/namespace.yaml
kubectl apply -f k8s/api-deployment.yaml
kubectl apply -f k8s/api-service.yaml
kubectl apply -f k8s/nginx-deployment.yaml
kubectl apply -f k8s/nginx-service.yaml
kubectl apply -f k8s/cron-deployment.yaml

# o HPA precisa do metrics-server, que é um addon do Minikube
minikube addons enable metrics-server
kubectl apply -f k8s/hpa.yaml

# conferindo
kubectl get pods -n daemon-lab
kubectl get svc  -n daemon-lab
kubectl get hpa  -n daemon-lab

O que se espera ver: 5 Pods Running (2 API + 2 Nginx + 1 cron), dois Services com NodePort 30080 e 30081, e o HPA mostrando o alvo de 50%.

Como acessar: curl http://$(minikube ip):30080/processes devolve o JSON com a lista de processos. Abrir /docs no navegador mostra o Swagger, onde dá para testar as rotas clicando. Para o site do Nginx: minikube service nginx-service -n daemon-lab.

Provas: 5pods.png, ProcessManagerAPI.png, nginx-k8s.png e nginx-k8s-terminal.png.

Se der errado: Pending = falta recurso ou imagem; ErrImageNeverPull = faltou o minikube image load; CrashLoopBackOff = o processo dentro do container morre — veja com kubectl logs.

Passo 10 — Derrubar um Pod e ver o self-healing

Para que serve: provar que o Kubernetes mantém o estado desejado. O YAML diz "2 réplicas"; se uma sumir, ele repõe sem ninguém pedir.

Pense assim: é um gerente que faz a contagem de funcionários a cada instante. Faltou um? Ele já chama outro.

# 1. veja os Pods e copie o nome de um da API
kubectl get pods -n daemon-lab

# 2. apague esse Pod
kubectl delete pod api-deployment-7487485766-2chk4 -n daemon-lab

# 3. assista a recriação acontecer
kubectl get pods -n daemon-lab -w

O que acontece, em ordem: o Pod é apagado → o ReplicaSet percebe que só há 1 em vez de 2 → cria outro com nome novo e a mesma etiqueta → em 9 segundos o novo está Running → o Service já começa a mandar requisições para ele.

A prova: RecriacaoPod.png.

Se te perguntarem "e se eu matar o container em vez do Pod?": aí é outro mecanismo. O kubelet reinicia o container dentro do mesmo Pod (por causa do restartPolicy: Always). O nome do Pod não muda, só a coluna RESTARTS aumenta. Dois níveis: container reiniciado pelo kubelet, Pod recriado pelo ReplicaSet.

Passo 11 — Gerar carga e ver o HPA escalar

Para que serve: provar o scaling automático. O HPA observa a CPU média dos Pods da API; se passar de 50% do que foi reservado, ele cria mais réplicas — até o limite de 10.

Pense assim: é o gerente que olha a fila e chama mais atendentes. Quando a fila acaba, ele dispensa os extras (mas com calma, para não ficar contratando e demitindo toda hora).

# terminal 1 — gera carga contínua na API (vai parecer travado, é normal)
while true; do curl -s http://127.0.0.1:<PORTA>/processes > /dev/null; done

# terminal 2 — acompanha o HPA
kubectl get hpa -n daemon-lab -w

# terminal 3 — acompanha os Pods nascendo
kubectl get pods -n daemon-lab -w

O que o grupo mediu: a CPU saiu de 2% em repouso para 204% sob carga, e as réplicas foram de 2 para 10 — em degraus (2 → 4 → 8 → 9 → 10), porque o HPA não pula direto para o máximo: ele recalcula a cada rodada. Parando a carga, a CPU caiu para 2% e, depois de uns 5 minutos (janela de estabilização), voltou para 2 réplicas.

A prova: hpa.png, replicas.png e replicasVoltando2.png.

Se te perguntarem "por que 204% e não 100%?": porque a porcentagem é relativa ao requests.cpu (100m). Se o Pod usou 204m, isso é 204% do pedido. Sem requests, o HPA não teria base de cálculo e ficaria em <unknown> — foi por isso que esse campo entrou no YAML.

Passo 12 — Registrar as provas e documentar

Para que serve: o edital não pede só "funcionou", pede prova. Print ou vídeo é o que transforma "confia" em nota.

5. As 8 frases que resumem tudo

Se você decorar só isto, já consegue contar o trabalho. Cada frase é uma resposta de 20 segundos.

  1. "O daemon serve para rodar em segundo plano, sem ninguém digitando." Nginx espera conexões, o cron espera o relógio.
  2. "Usamos três daemons diferentes porque o edital exige três containers com daemons distintos." API (uvicorn), Nginx (nginx + crond) e cron isolado.
  3. "A API é a ponte entre quem pergunta e o sistema operacional." Ela usa psutil para ler os processos e subprocess para iniciar.
  4. "O hostPID: true é o que faz a API enxergar o nó inteiro." Sem ele, ela só veria os processos do próprio container.
  5. "O Docker empacota; o Kubernetes mantém o estado desejado." Docker constrói a imagem; o Deployment garante as réplicas.
  6. "O self-healing é o ReplicaSet repondo o que caiu." Apagamos um Pod e em 9 s havia outro no lugar.
  7. "O HPA é o gerente que contrata mais quando a fila cresce." Com CPU em 204% do pedido, foi de 2 para 10 réplicas.
  8. "As provas são os prints; a explicação está na documentação." 21 prints, três tarefas, um README.

6. Se você só entendeu metade

Versão de 30 segundos

Fizemos três programas que ficam rodando sozinhos (API, Nginx e cron). Empacotamos cada um num container. Colocamos os três dentro do Kubernetes, que é o gerente: ele mantém as cópias no ar e cria mais quando a carga sobe. A API é a única que mexe nos processos do sistema — e ela só consegue isso porque pedimos ao Kubernetes para dar a ela visão dos processos do nó. Testamos derrubando um Pod (voltou em 9 s) e gerando carga (foi de 2 para 10 cópias).

O que responder se travar

Respire e use a estrutura: "isto serve para…", "nós usamos … porque…", "o arquivo … faz…". Você não precisa lembrar de comando; precisa lembrar do motivo. E se for algo que não estudamos: "não implementamos isso; o mais próximo que temos é X, e para resolver eu faria Y".
